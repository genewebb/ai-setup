CrewChief has TWO copies of the `CreateStepForType(string type)` switch — one in `CrewChief.Web/Components/Pages/Steps.razor.cs` and one in `CrewChief.Web/Components/Pages/WorkloadEditor.razor.cs`. Both switch on the canonical type key from `Helpers.UtilityStepTypeInfo.AllTypes` and fall through to `_ => new CommandLineStep()`.

A step type listed in `AllTypes` but MISSING from a factory silently creates a CommandLineStep instead. This exact bug hit `"SetApiKey"` (it was in AllTypes but neither factory had a case) → picking "Set API Key" produced a Command Line step. FIXED 2026-07-16 by adding `"SetApiKey" => new SetApiKeyStep()` to both.

**How to apply:** when adding any new UtilityStepBase step type, update ALL of: the step class, `StepTypeRegistry` (single dispatch source — `UtilityStepConverter` + `CreateFromJToken` both consult it, so ONE Register<T>() line covers deserialization), the engine executor + its DI registration in `EngineServiceCollectionExtensions`, `UtilityStepTypeInfo` (AllTypes + icon/name/desc/colors), the `StepEditorCard.razor` type branch, AND **both** `CreateStepForType` factories. Consider consolidating the two factories into one shared helper to remove this footgun. Relates to [[project_crewchief_standalone]].

Engine has NO project references (no Binder → no `IConfiguration.GetValue<T>`; use the indexer + manual parse).
