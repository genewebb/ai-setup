2026-07-19 CrewChief config/UX changes (verified green via workflow).

**HTTPS cert policy (CrewChief.Web/Program.cs):** cert is resolved ONCE before Kestrel config. Thumbprint may live in EITHER source (or both): appsettings `WebUI:Certificate:Thumbprint` (shipped placeholder `REPLACE_AT_DEPLOY_...`) OR the loaded /secrets store `Certificates:LocalHttpCertificateThumbprint` (per-box, authoritative). Resolution collects candidates SECRETS-FIRST and uses the FIRST that resolves to an installed `LocalMachine\My` cert — so the appsettings placeholder (non-empty but bogus) simply fails to match and falls through (no placeholder-detection heuristic needed). Secret key mapping confirmed: a `Certificates` section with value `LocalHttpCertificateThumbprint` flattens via SecretSchema to config key `Certificates:LocalHttpCertificateThumbprint`. If NO candidate resolves, HTTPS is unbound — app runs HTTP-only, prints a boxed `Console.WriteLine` "HTTPS DISABLED / ACTION REQUIRED" message naming BOTH keys + a Serilog warning, and the startup URL banner omits the https URLs. There is NO dev-cert fallback — do NOT "restore" the old argument-less `lo.UseHttps()` (removal is intentional, operator request). Startup log reports which source the cert came from. See [[project_crewchief_secrets_local_json_eliminated]].

**IisReset executor-resolution bug (found on deploy 2026-07-20, FIXED):** running an IisReset step failed validation with `No executor found for step type 'IisReset'`. Root cause: `UtilityOrchestrator` keys `_executorsByType` by `executor.StepType` then adds an alias for each step's short canonical `Type` (`AddExecutorAlias("SQL","SqlStep")`, `("SetApiKey","SetApiKeyStep")`, etc.). `IisResetStep.Type = "IisReset"` but `IisResetExecutor.StepType = "IisResetStep"` — and IisReset was the ONE step MISSING from the alias list. Fix = add `AddExecutorAlias("IisReset", "IisResetStep")` (NOT changing StepType — that would make IisReset the lone inconsistency and break the StepType_IsIisResetStep test). Regression test added: `IisResetExecutorTests.ValidateScenario_IisResetStep_ResolvesExecutor`. LESSON: earlier verification workflows checked verbiage/target-parity/build but NOT end-to-end executor resolution — the gap that let this ship. When adding/renaming a step type, verify `UtilityOrchestrator` has an alias mapping its `.Type` → `executor.StepType`.

**IisReset step (req: "verbiage should say start, stop and recycle, not recycle" + "make it work like services"):** the target-machine support was ALREADY fully wired (model `TargetComputer`, executor, `ServerNameEditor` in StepEditorCard, both `CreateStepForType` factories, `StepTypeRegistry`) — the user's "no target machine" was a STALE published build, not missing code. Only the verbiage was wrong. Changed: `UtilityStepTypeInfo` display name "Recycle IIS" → "IIS Reset", description → "Start, stop, or recycle IIS (iisreset)..."; `IisResetActions` reordered to `{ "Start", "Stop", "Recycle" }` (mirrors ServiceControl's `{ Start, Stop, Restart }`); and 5 in-app help docs (28_StepGuideIisReset.md title/heading/summary, 10_StepGuideIndex.md, 02_ManualSetupAndTesting.md, 43_OpsRemoteBoxPrep.md, 34_OpsReferenceData.md) had the step-NAME label "Recycle IIS" → "IIS Reset" (the "Recycle" ACTION verb left intact). Doc route/slug stays `iisreset`.
