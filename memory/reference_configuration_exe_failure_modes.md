Profisee `Configuration.exe` (26R2, `platform` repo `Server\Configuration\Program.cs` @ tag `2026R2`) **always exits 0** — validation errors print-and-return and the outer try/catch logs exception dumps then prints "The operation completed successfully." Failure detection must scan output. CrewChief's `ConfigureExecutor.DetectConfigurationFailure` catches `Missing parameter \S+` AND (since 2026-07-22) `StackTrace =` exception dumps, surfacing the `Message =` line.

Known failure modes (SMVM3 box-prep, 2026-07-22):
1. **`Missing parameter <name>`** — required switch absent (`HasSwitch` checks key presence only). 26R2 requires the maestro-service trio (`maestroServicePort`/`maestroServiceUserName`/`maestroServiceUserPassword`); these were REMOVED on platform master (monolith→web-app change), so **master's Program.cs is the wrong reference for 26R2 boxes** — use tag `2026R2`. Correct password switch name is `maestroServiceUserPassword` (NOT `maestroServicePassword`).
2. **Single-frame NRE at `CommandLine.Run`** — the `useHttps` switch being PRESENT (any value) runs `new ServerManager(); manager.Sites[webSiteName].Bindings...` during arg parsing, before license/SQL checks. `SiteCollection[name]` returns **null** (no throw) for an unmatched site name → NRE. It means the site NAME the exe received doesn't exist — either IIS genuinely lacks it, **or the name was truncated by argument mangling** (live case: CrewChief's compose-quote-before-token-resolve bug sent `/webSiteName:Default` + stray args `Web` `Site`; fixed by `ComposeArgumentString(resolveValue)` overload — see [[project_crewchief_configure_switches]]). Diagnostic: "Configuring Profisee - Done getting parameters" absent from output brackets the crash to the parameter section; NRE (vs FileNotFound=no IIS config / UnauthorizedAccess=non-admin) proves IIS config was read fine.

3. **NRE in `LoadConfig()` / `writeServiceConfig(...)`** — Configuration.exe derives ALL its paths from the **current working directory** (`WebAppConfigurationContext` ctor: `PhysicalPath = Directory.GetParent(Environment.CurrentDirectory)`), NOT from its exe location. It must be started FROM its own `...\<ver>\Configuration` folder. The LoadConfig NRE is swallowed (run continues); writeServiceConfig NRE kills the service-config write. Path signature of this mode: errors referencing `C:\Users\Services\...` (= `..\Services` resolved from a home-dir CWD — a WinRM session's default CWD is the Run As profile, so an OLD CrewChief remote run shows exactly this). CrewChief defaults the Configure step's working dir to the exe's folder (local + remote via `RemoteRunRequest.WorkingDirectory`/`CC_REMOTE_WORKDIR`) — **only in builds ≥ commit `4f3f7b2a` (2026-07-22)**; a deployed CrewChief older than that reproduces this mode on every remote Configure (confirmed live 2026-07-24 on CORPVMHA1: same switches from the Configuration folder succeed). The editor's copy-paste preview also emits a leading `Set-Location "<exe folder>"` (added 2026-07-24) so hand-run pastes are safe from any CWD. **Confirmed live 2026-07-22 on SMVM3**: the minimal 19-switch invocation succeeds once started from the Configuration folder — CWD was the sole root cause; the wider canonical switch set is for determinism, not correctness.
   - Follow-on trap: a run in this failure mode may still REGISTER the platform Windows service; if that run also had masked secrets pasted literally (`********`), the service is stamped with a bogus password → the NEXT (correct) run fails only at `SaveService` with **service start error 1069 logon failure**. Fix: `sc.exe config "Profisee <ver> (Profisee)" obj= "<user>" password= "<real>"` (or services.msc), start it, re-run Configure.
4. **`Login failed for user 'NT AUTHORITY\ANONYMOUS LOGON'` from SQL** — Kerberos double-hop: CrewChief host → WinRM → target → Windows-auth SQL on a third box. Fix = step's Authentication picker → CredSSP (`remoteAuthentication` on all 6 remote steps, wired 2026-07-22) + `Enable-WSManCredSSP -Role Server` on target / `-Role Client -DelegateComputer <target-FQDN>` on CrewChief host; or SQL login switches. Setup doc: `43_OpsRemoteBoxPrep.md` §5.

Also: `CommandLineParser.ParseOptions` ABORTS all remaining arg parsing on the first duplicate switch key (early `return`) — duplicates silently drop every later switch. Non-slash tokens become ignored positional arguments. (`platform\Common\Common\CommandLineParser.cs:101-105`; accepts both `/` and `-` prefixes, `:` or `=` separator, strips quotes. Nothing ever reads `DuplicateSwitches` — grep: zero consumers.) Note `platform\Server\node_modules\@rushstack\ts-command-line` also matches a `CommandLineParser` grep — unrelated npm package, and grepping `platform` unfiltered times out ripgrep on it.

## SQL authentication — two credentials, not one (read at platform HEAD 2026-08-07, NOT verified against tag `2026R2`)

`/sqlUserName` + `/sqlUserPassword` are the **installer** credential only — what Configuration.exe itself connects with to build the DB. The **runtime** login is generated: `getSqlUserName()` returns `Profisee_{MaestroDatabaseName}_{FQDN}` (`WebAppConfigurationContext.cs:280-285`) with `SqlPassword = Guid.NewGuid().ToString()` (`:2854`, `:5254`, `:5507`), created by `Script.UpdateSecurityForSql.sql:33-37`.

- **Which auth the INSTALLER uses**: `useWindowsAuth && string.IsNullOrEmpty(sqlUserName) ? WindowsIntegrated : SQLLogin` (`Program.cs:928`, `:613`). So `/sqlUserName` alone flips the setup connection to SQL auth.
- **Which auth the INSTANCE gets**: `context.UseWindowsAuthentication = useWindowsAuth` (`Program.cs:888`) — the flag ONLY, `sqlUserName` irrelevant. Drives runtime connection strings (`WebAppConfigurationContext.cs:2695`) and which identity gets DB grants (`DatabaseUtilities.cs:918-970`: `UpdateSecurityForWindows.sql` + `AppPoolUserName` vs `UpdateSecurityForSql.sql` + generated login).
- **Split-brain trap**: `/sqlUserName` without `/useWindowsAuthentication:FALSE` = installer connects over SQL login, instance provisioned for Windows auth. Exits 0.
- **LOCKOUT trap**: `var adEnabled = useWindowsAuth;` (`Program.cs:391`). SQL auth turns the Windows sign-in provider OFF. With OIDC off that leaves no provider at all. **Always pair `/useWindowsAuthentication:"FALSE"` with `/authAdEnabled:"TRUE"`.**
- **Installer login must be sysadmin**: `Script.UpdateSecurityForSql.sql:10-27` gates `prof_dlp_login` creation + `ALTER AUTHORIZATION ON DATABASE` on `IS_SRVROLEMEMBER('sysadmin')`, ELSE only `PRINT`s. dbcreator+securityadmin silently yields a half-secured DB. Verify: `SELECT SUSER_SNAME(owner_sid) FROM sys.databases WHERE name='<db>'` should be `prof_dlp_login`.
- `useWindowsAuthentication:FALSE` with empty `sqlUserName` DOES throw (`DatabaseServerInformation.cs:87-93` `ArgumentNullException`) — caught by CrewChief's `StackTrace =` scan. Loud, not silent.
- `.ProperEquals` is `InvariantCultureIgnoreCase` (`Extensions.cs:668`) so `"false"`/`"FALSE"` both work.

**Why it matters**: SQL auth removes the DB from the Windows-identity chain — local (non-domain) service accounts become viable and the WinRM CredSSP double-hop disappears. See [[project_smvm2_profisee_identity_drift_chain]].

Documented into CrewChief 2026-08-07: `41_ReferenceConfigurationSwitches.md` § SQL authentication, `25_StepGuideConfigure.md` (three silent pairings + SQL-auth example), `ConfigurationSwitchCatalog.cs` descriptions. Those docs previously claimed "Configuration.exe rejects duplicate switches" — false, now corrected.

CrewChief lesson: the editor's PowerShell preview resolves-then-quotes, the runtime used to quote-then-resolve — preview can look correct while the real command line is broken. Both now resolve before quoting.
