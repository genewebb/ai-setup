Symptom chain reported 2026-07-31: tick steps/workloads → **Check Capability** → dialog shows results but the per-row Capability icons never change; and a bulk check reported a FAILURE that checking the same steps individually did not. **Three separate causes**, all fixed. The user's invariant: *a bulk check must produce the same results as an individual check, and the icons must update either way.*

**Cause 1 — badge memo never invalidated (Steps page).** `CapabilityBadge.OnParametersSetAsync` early-returns on `_evaluatedFor.SequenceEqual(Steps)` (element-wise REFERENCE compare). `PreflightAsync` writes the cache but never touches the `Steps` parameter, so a mounted badge never re-read. Fix: `ICapabilityAdvisor` now exposes `event Action? VerdictsChanged`, raised **coalesced once per call** from `PreflightAsync`, `EvaluateStepAsync` (demanded-probe branch) and `Refresh`; `CapabilityBadge` subscribes in `OnInitialized`, re-reads via `LoadAsync(allowNetworkProbes: false)` through `InvokeAsync`, skips while `_probing`, and is `IDisposable`. **Only affects the Steps page** — on Workloads `PreflightGate.cs:159` re-deserializes `entry.Inline.ToObject<UtilityStepBase>()` on EVERY call and `Workloads.razor:165` calls it every render, so instances are always fresh and that memo never engaged there. (The `WorkloadStepMaterializer` doc claiming it returns the same instance "so the badge's `_evaluatedFor.SequenceEqual` guard keeps working" is defeated one layer up by that `ToObject`.)

**Cause 2 — deferral and caching predicates had drifted. THE reason the icons stayed gray.** The render path deferred `IsNetworkCapability(cap) || UsesRealCredential(cap, identity)`; `CacheIfConclusive` gated on `IsNetworkCapability` **alone**. So a Run-As `LocalAdmin`/`LocalLogon` was deferred on every render but cached by nothing — every render recomputed `NotProbed` → **permanently gray on every parameter-driven box-prep workload**, unchangeable by bulk check, run preflight or Probe. The gate was never widened when the Run-As credential deferral (design §6a / D5b, LocalLogon) was added. Fix: single `CapabilityAdvisor.DeferUntilAsked(capability, identity)` read by BOTH paths, so they cannot drift again; `CacheIfConclusive` takes `identity`. **Rule: cache exactly what a render refuses to answer.**

**Cause 3 — preflight dedup collapsed step-scoped requirements, so bulk ≠ individual.** `ProbeKey` was (capability, target, detail, identity) with **no step**, but the three seam-backed probers (`SqlAuthProber`, `ShareFirstHopProber`, `ShareSecondHopProber`) resolve their real connection string / share mount from `CapabilityStepScope.CurrentStep`. Two steps sharing a requirement triple were collapsed — the first was probed under ITS scope, the second `continue`d with **no verdict of its own** — so one step's failure stood in as the answer for both, and a bulk check disagreed with checking them singly. Fix: new `CapabilityAdvisor.ResolvesFromStepScope(capability)` (SqlAuth | ShareFirstHop | ShareSecondHop); `ProbeKey` gains a step discriminator populated **only** for those (reference equality). Step-independent capabilities (LocalAdmin/LocalLogon/RemoteRunAs/RemoteWinRm — none take a seam) still collapse on the triple, so "fifteen steps against one box = one WinRM handshake" is preserved and pinned by its own test.

**Cause 4 — tokenized targetComputer derived an unanswerable WinRM requirement (reported later on 2026-07-31: "bulk check completes but Workloads-page icons never change").** The shipped `26r2-parm-driven-*` workloads carry `targetComputer: "{{$config:ServerNames:ApplicationServerName}}"`. `StepCapabilityRequirements.For` is pure and emitted the token VERBATIM as `Requirement.Target`; `RemoteWinRmProber` (correctly) returns Unknown for any target containing `{{`, and Unknown is deliberately never cached — so every bulk check/preflight "completed" without answering and the badge's cache-only re-read stayed `NotProbed` gray forever. Worse, the verbatim token never looks local, so a token naming THIS machine still derived the REMOTE pair. Fix: `For(step, resolveText?)` — an optional injected resolver (purity preserved by injection) applied to `targetComputer` + `remoteAuthentication` for the box-prep six + Install, mirroring `BoxPrepRouting.Decide` which judges locality on the RESOLVED target. `CapabilityAdvisor` gained a trailing-optional `resolveTokenText` ctor seam (adapted per step via `TargetResolverFor`), wired in `CapabilitySubsystemRegistration.ResolveTargetTokenText` to the executors' `ITextTemplater` over the step's (materializer-merged) Parameters. Requirements now carry the resolved machine → probeable, cacheable under the same key a render re-derives, dedup collapses same-box tokens, `Refresh(target)` invalidates by real name. Unresolvable token keeps verbatim shape (honest Unknown, unchanged). Defense-in-depth: `RemoteWinRmProber` also returns Unknown (never probes) when a target `IsLocalTarget` — loopback WinRM would re-create the D5b false block. NOT applied to HealthGate (its executor tests the UNRESOLVED field) nor SqlAuth/share targets (their probers' seams resolve those; pre-resolving a SqlStep secret-name token would inject a live connection string into the key). Red-first verified; suite 2628/2628.

**Scope discriminator (fixed since the note below was written).** `CapabilityRequirement` gained a never-rendered `Scope` field, included in the cache comparer and ProbeKey — DB name for built SQL targets, share-credential type|user for mounts — closing the DatabaseOperations-vs-SetApiKey cross-served-verdict case.

**STILL OPEN — the same flaw one layer over, in the cache.** `CapabilityProbeCache` is keyed by (capability, target, detail) with no step, and `AnswersFor` validates only IDENTITY. So for the three seam-backed capabilities the cache can serve step A's verdict to step B, and now that both steps probe, they write the same key last-writer-wins. Two SqlAuth steps against one server with different databases/credentials can show each other's answer. Fix shape: give the cache key the same step/resolved-target discriminator, or have the requirement carry the resolved target. Not a run-safety hole — `PreflightAsync` bypasses the cache READ entirely, so a gating decision is never made on a cached verdict; it is a badge-display defect only.

**Testing notes.** `CapabilityBadgeTests.CreateContext` registers ONLY `advisor.Object`, which is why `VerdictsChanged` lives on `ICapabilityAdvisor` and not on `CapabilityProbeCache` — injecting the cache into the badge breaks all existing badge tests on DI resolution. Moq records `add_`/`remove_` accessors in `Invocations`, so assert on `EvaluateStepAsync` counts, never `Invocations.Count`. `LocalLogon` is derived from the **step** declaring a Run As (`CredentialUserId`+`CredentialPassword` on a local box-prep step → LocalAdmin+RemoteRunAs+LocalLogon), NOT from the resolved identity — setting only the identity seam derives no LocalLogon requirement. Both fixes were verified red-first by temporary revert (dedup: `Expected:<2>. Actual:<1>`).

Not a bug, do not "fix": `Unknown`/`NotProbed` are deliberately never cached, so a genuinely unanswerable check stays gray after any reload (spec D2, and Unknown never blocks).
