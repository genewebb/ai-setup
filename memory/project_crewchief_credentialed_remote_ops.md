**Root cause (2026-07-20):** Installed CrewChief service runs as LocalSystem (`installer\CrewChief.iss:141/:144`) → remote SCM/IIS ops authenticate as the machine account and fail (SMVM3 "Cannot open Service Control Manager"; denied SCM open also masquerades as "service does not exist"). THREE ambient-identity remote paths confirmed: ServiceControl (`ServiceController`, RPC), AppPool (`ServerManager.OpenRemote`), IisReset (`iisreset <computer>`). Box-prep steps (Install/Uninstall/Configure) are immune — they use `IRemoteCredentialResolver` + `DefaultRemoteCommandRunner` (credentialed WinRM).

**Decision:** Option B — route the three through the existing credentialed transport; optional `credentialSecretName` per step; remote-without-credential keeps legacy ambient fallback + warning (deliberate divergence from box-prep §3.2 for back-compat). User will stay on Windows 3–12 months, then likely **Linux** containers (not Windows) — so C (LogonUser impersonation) and A (gMSA) were rejected; only IRemoteCommandRunner needs a pwsh/SSH swap later.

**Plan:** `C:\devopslocal\ObsidianVaults\Work\MyWorkVault\99 Documentation\speed-merchants\planning\Plan_CredentialedRemoteServiceOps.md`.

**Secrets reload didn't propagate to the app (2026-07-21, FIXED):** editing a Local Secret (or Reload/Replace on /secrets) updated the /secrets view (reads the store directly) but NOT the step editor / token resolution — those read `IConfiguration` via `SecretCatalog`, which stayed frozen at startup. ROOT CAUSE: `IConfigurationRoot.Reload()` on the minimal-hosting **ConfigurationManager does not reliably re-run a source Added after build**, so `LocalSecretsConfigurationProvider.Load()` never re-decrypted; and Load() swallowed all failures silently. NOT master-mismatch (you can only save under the store's master) and NOT a path/instance mismatch (Program.cs registers the SAME `localSecretStore` instance the config source uses). FIX: `LocalSecretsConfigurationSource.ReloadNow()` (caches its built provider, calls `provider.Load()` + `OnReload()`), registered as a DI singleton; `SecretsManagement.ReloadConfiguration()` calls it alongside `root.Reload()`; `Load()` now logs each outcome (section/key count on success, warning on master-unresolved/0-sections/decrypt-fail) so a silent stale-keep can't recur. No app restart needed after this. 1420/1420 green.

**Also relevant:** interactive (non-service) install mode is a first-class installer option (uncheck the `service` task; console shortcut + `[Run]` autostart exist) and sidesteps the whole identity problem while B is unbuilt.
