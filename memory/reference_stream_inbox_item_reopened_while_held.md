A `taken` line in `.streams/inbox/<skill>.md` does not stop the same id coming back as `open`, and **the session named on the re-opened line is the item's original filer, not whoever re-opened it**. On 2026-09-30 `IN-20260930132935-5281` (amend the G6.T071/G6.T102/G6.T104 tickets and graders) was taken by `author-...-e6ed` at 13:53:53Z, re-opened at 14:33:01Z carrying `coord-202609291248`, and taken by `author-...-fffd` at 14:40:09Z, which began writing an amendment e6ed had already finished at 14:00-14:09Z. e6ed filed two items accusing the coordinator. The real actor is in `decisions.md`: `[status-79edb8dd] watchdog: RELEASED ... holder silent on the board since 13:21:40Z`.

**Why:** `Invoke-Watchdog.ps1`'s inbox sweep releases any `taken` item whose holder has not touched `tasks.json` for the role limit, and it re-appended the item as a byte copy of the filing. `Test-HolderWorking` builds its evidence only from `tasks.json` history and claim beats, so a holder working a **prose-only item** — ticket and grader wording over rows nobody claims — writes nothing the watchdog can see and is reaped every time. `Read-InboxItems` also takes kind, task, ask and evidence from the FIRST line of an id, so the re-opened line said nothing about being a re-open.

**How to apply:** never read the `by` column of an `open` line as the re-opener — check `decisions.md` for a `RELEASED <id>` line first. Since 14:55Z 9/30 the kit says so itself: the by column reads `<filer> (WATCHDOG RE-OPEN, previous holder <who> silent <n> min)` and the ask begins `RE-OPENED BY THE WATCHDOG`, guarded by four cases in `Test-StreamKit.ps1`; `$seen` now also counts inbox events, which does **not** save a holder whose only event is its own `taken` line. Before starting any re-opened item, check the task's ticket, grader and verdict for work already done. Related: [[reference_stream_author_takeover_race]], [[reference_stream_stale_read_blocks_and_bugs]], [[reference_live_session_does_not_reread_skill_md]].

**Second occurrence, 2026-09-30 17:08Z, and the reason it will keep happening:** the skill's step 7 mandates ONE skeptic subagent round; mine on `IN-20260930153050-3179` ran 54 minutes (246,944 tokens), and there is no `-Beat` for an inbox item, so the watchdog re-opened the item — `previous holder author-202609291625-b3d7 silent 89 min` — and a second author took it at 17:19Z and closed it `done` at 17:32Z, describing edits the first session had made. Nothing was lost only because the graders on disk still hashed to the first session's versions. **A task claim survives a long subagent because `Update-Task -Beat` exists; an inbox item has nothing to beat.** So: while working an inbox item, touch `tasks.json` at least every 20 minutes (a status-role `-Note` on a related task counts, since `$seen` reads history), and before appending `done` re-read the item tail and compare the artifacts' hashes with what you wrote. Kit fix requested in `IN-20260930173837-50cb` (stream-kit): a `-Beat` status for inbox items, the watchdog reading the LATEST line, or a silence threshold above a real skeptic round.

**FIXED 2026-09-30 18:09Z, so beat instead of working around it.** `Set-InboxItem.ps1 -Status beat` exists: `Set-InboxItem.ps1 -Repo <r> -Skill <skill> -Id <id> -By <session> -Status beat -Note '<what is running>'`. It moves the hold's clock and nothing else - the item stays `taken` by the same holder - and **only the holder may beat** (`NOT-HELD`, exit 8, otherwise, which is stricter than `done`). `lib\Inbox.ps1` reads a `beat` line as a heartbeat under the hold rather than a status, so `Get-InboxItems` stops offering the item as overdue. Call it inside any step that can outlast the role's inbox limit - the mandated skeptic round above all - and the touch-tasks.json workaround above is no longer needed. Six cases guard it in `Test-StreamKitRecovery.ps1` (two 90-minute holds side by side, only the unbeaten one released). `stream-author` SKILL.md step 0 and the `stream-kit` script table say so, but a live session does not re-read SKILL.md: see [[reference_live_session_does_not_reread_skill_md]]. The same install also taught the watchdog that **a fresh beat is not progress** - an author claim is broken when the row's own artifacts and the holder's own history have not moved for 60 minutes, measured after G4.T039 beat for 19h14m writing nothing; build is exempt.
