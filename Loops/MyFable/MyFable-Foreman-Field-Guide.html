How the /myfable skill works

MyFable Foreman

A way to work through a long list of coding tasks with AI helpers. One session plans each job and judges the result. Cheaper workers do the job. Scripts do the paperwork. Nothing counts as done until a check that was failing before the work starts is passing after it.

You

Approve the human gates. Nothing past a gate runs until you say so.

Lead session

Writes each ticket and its check, reads the results, accepts or rejects. Nothing else.

Scripts

Refuse unsafe dispatches, run the checks, keep the records, rebuild the board.

Workers

Opus agents, up to 7 at once. Each does one ticket and reports back.

Verifier

A fresh agent that never saw the worker's reasoning and assumes the work is broken.

One turn, start to finish

The loop

Each task on the board is a row. A turn takes one row (or several that can't collide) from "ticket written" to "closed". Read the picture left to right; each horizontal band is one of the five players above.

  1. 1Write the ticket. One file, .loop\PLAN-<key>.md. The top block tells the scripts the kind of task, its check, its estimate and which files it may touch. The body tells the worker what to do. The lead also writes a check (grader) that fails right now, and a self-test proving the check can tell wrong work from right work.
  2. 2Dispatch-Row.ps1 refuses the whole batch if anything is unsafe (see below). If it's happy, it writes the row record, marks the row Started, rebuilds the board, and prints the exact worker prompt and monitor command.
  3. 3Launch. Publish the updated board, then start one opus worker and one monitor per row. Arm /loop as a slow backup alarm.
  4. 4Monitor runs the row's check every minute. The moment it passes, the session wakes. (A finished background agent alone doesn't reliably wake a quiet session. That was measured on 9/9, and it's why the monitor exists.)
  5. 5The worker reads the ticket, changes only files in its write set, runs the check until it passes, and reports. It never commits, never starts other agents, never publishes.
  6. 6Collect-Row.ps1 records the report, runs the checks for that kind of task, and prints one verdict sheet. It never accepts anything.
  7. 7Read and decide. The worker's report is a claim, not proof. The lead reads the sheet, the report and the changes. Reject means a sharper ticket and another attempt. A third attempt on an unchanged ticket isn't allowed.
  8. 8Blind verifier for code and security rows. It gets the original ticket and the changes, never the worker's reasoning. Its verdict is evidence. Acceptance is still the lead's call.
  9. 9Close-Row.ps1 requires a "residual" answer (none, or the row that carries the rest). It then records actual minutes, writes a one-line board status and rebuilds the board and the two vault status pages. After that comes a compact prompt: y/n, and no answer in 60 seconds means no.
  10. 10Gate. At a gate row the loop stops. For mockups, the whole batch is published as one page for you to review. Only your words, run through Approve-Gate.ps1, unlock the rows behind it.

A task's life

Every row has one JSON record, written only by the scripts. It's the single source of truth, and the ledger and board are rebuilt from it. Here are the states a row can be in, and which script moves it between them.

Dispatch-Row.ps1, before any worker starts

What gets refused

These are the rules that used to live in the lead's head and now live in a script. If any row in the batch breaks one, nothing in the batch is dispatched.

The check already passes

If the grader is green before any work, the row would "close" having done nothing. Checks must fail first, for the reason the ticket states.

The self-test fails

A check that can't tell a wrong stub from a correct one proves nothing. The named self-test must pass.

Workers could collide

Two rows in the batch, or a new row and one already running, list write sets that might touch the same file.

A gate is still closed

The row names a gate (afterGate) that you haven't approved yet.

Too many, or malformed

More than 7 keys; missing key, class, grader, estimate or write set; a class other than mockup, doc, code or security; the row already running.

scripts\checks\<class>.ps1

Proof depends on the kind of task

Not every task deserves the same scrutiny. A static HTML mockup can't leak a password to production; a login change can. Each row picks a class, and the class decides which checks run and whether a verifier is needed.

Up to seven workers at once

Running in parallel

Workers can run side by side only if they can't write to the same file. The script decides this with a deliberately cautious test: it takes each write-set pattern, cuts it off at the first *, and treats the rows as colliding if one leftover path starts with the other. In practice, that looks like this:

Different folders
A: src/Web/Secrets/*.csB: src/Web/Cards/*.cs
✓ Runs in parallel

Neither leftover path starts with the other.

Same folder, different files
A: ui/kit/*.htmlB: ui/kit/NOTES.md
✕ Refused

Refused even though .html and .md never meet. A wildcard in a folder blocks every other row that writes anywhere in that folder.

Hidden shared file
A: src/Web/Secrets/*.csB: src/Web/Cards/*.csboth must also edit tests/CENSUS-INVENTORY.md
✕ Can't really run together

The worker rules require every new test file to be recorded in the census file. Leave it out of both write sets and one worker gets blocked. Put it in both and dispatch refuses.

Rules of thumb from the skill: code rows fan out only when their write sets don't overlap and they don't share a test project. When in doubt, run them one after another, because a collision costs more than the wait. One board publish per fan-out, one monitor per worker, collect them in whatever order they finish.

How to make it better

Each suggestion is tagged by how we know it's a problem. seen means it already happened in a real record. in the code means the scripts provably behave this way today. risk means it's reasoned from the design and hasn't been seen yet.

  1. Re-run earlier rows' checks when a row closes

    seen

    TodayCollect-Row runs only this row's check. A row can quietly break a check an earlier row made green, and still close green.

    ChangeAt collect, find closed rows whose write sets touch this row's changed files and re-run their checks. Keep the daily full sweep as a backstop.

    Evidence: checks\*.ps1 run only $row.grader. Under the previous loop, 7 once-green checks were found broken after 3 days of closes (memory note, 8 Sep).

  2. Refresh the change baseline after every accepted code row

    seen

    TodayThe "only allowed files changed" check compares against BASELINE.json. When that baseline is older than the last closed row, the previous row's files show up as violations.

    ChangeClose-Row retakes the baseline after it accepts a code or security row. The existing rule is kept: never after a failed row.

    Evidence: 52.P1.3b closed with -Override: "BASELINE.json iteration 187 predates closed row 52.P1.3a".

  3. Calibrate estimates, then derive the alarms from them

    seen

    TodayRows ran at 0.30× their estimates. The "overdue" flag fires at 3× the estimate, which is roughly 10× real time. The monitor gives up after a fixed 120 polls (2 hours) no matter the row's size.

    ChangeKeep a per-class factor from actuals (Close-Row already writes actuals.json). Base "overdue" and the monitor timeout on the calibrated estimate.

    Evidence: Reconcile-Rows.ps1:25 (3× est), Dispatch-Row.ps1:120 (120 polls, 60 s).

  4. Don't collect a row until the worker has reported

    risk

    TodayThe monitor wakes the session when the check turns green, which can happen before the worker is done (it may still be writing notes or tidying). Collect-Row accepts an empty status.

    ChangeMake -Status required on the collect form. A green monitor then means "look for the report", not "start judging".

    Evidence: Collect-Row.ps1:9 allows ''. No recorded case of an early collect yet.

  5. Turn "no third try on the same ticket" into a script check

    in the code

    TodayThe skill forbids a third attempt on unchanged input, but only the lead's discipline enforces it.

    ChangeStore a hash of the ticket and check with each attempt. Dispatch-Row refuses attempt 2+ if both are unchanged.

    Evidence: Dispatch-Row.ps1 has no attempt limit. 52.P1.3c went to 4 attempts; each one did change the ticket (C13, C14, C15), so it was legitimate.

  6. Make the gate insist on the batch verifier

    in the code

    TodayApprove-Gate records approval without checking that the mockup batch was verified. In the record, the verdict sits on one row of the batch, so the record alone can't show the whole batch was covered.

    ChangeStore the batch verdict on a batch record. Approve-Gate refuses if any row behind the gate lacks one.

    Evidence: Approve-Gate.ps1 (18 lines, no checks). Rows 1a exempt, 1b blank, 1c pass with notes.

  7. Handle files every row must touch

    risk

    TodayShared "append a line" files (the test census, sample-data.js) either block parallel runs or cause blocked deviations.

    ChangeAdd an appendOnly: list to the ticket. Workers write their lines to a side file, and Close-Row merges them. Overlap checks ignore these files.

    Evidence: PROMPTS.md code rules ("a test file you add must be classified in tests/CENSUS-INVENTORY.md"). Mockup rules allow appending keys to sample-data.js.

  8. Move project-specific values into a per-repo config

    in the code

    TodayThe scripts assume this programme: both speedy repos as defaults, a secrets pattern naming your machines, a .NET-only test summary, a helper path inside the old loop skill, and board scripts under .loop\tools.

    ChangeAdd a .loop\foreman.json with repos, secret patterns, test-summary pattern, board commands and the status page name and key pattern. The scripts read it and fall back to today's values.

    Evidence: Dispatch-Row.ps1:91, checks\mockup.ps1:43, checks\code.ps1:15, Collect-Row.ps1:16, RowCommon.ps1:110–123.

  9. Bring the docs in line with the model decision

    in the code

    TodaySKILL.md says Fable plans and verifies. On 12 Sep at 22:09 you switched the session to opus, with one ticket written ahead. Collect-Row still stamps every verifier verdict as "fable".

    ChangeUpdate principle 1 and the verifier header. Pass the verifier model as a parameter so the record says what actually ran.

    Evidence: SKILL.md principle 1, PROMPTS.md § Verifier, Collect-Row.ps1:37.

  10. Work out minutes instead of typing them

    in the code

    TodayClose-Row requires -Minutes by hand, even though each attempt already stores when it was dispatched and collected.

    ChangeDefault to the sum of attempt durations. Keep -Minutes as an override.

    Evidence: Close-Row.ps1:10, Collect-Row.ps1:49 (collectedAt).

Setting it up for a new list of tasks

Tailoring it to new work

The skill is built around one question per task: can you write a check that fails now and passes when the job is done? If yes, everything else is just choosing the right class, write set and gates. If no, the task isn't ready to be a row yet.

Plain meanings

Words used here

Row
One task on the board, with a key like 52.P1.3c. Integer rows like 60 are human gates.
Ticket
.loop\PLAN-<key>.md. The top block is for the scripts, the body is for the worker.
Grader (check)
A script that exits 0 only when the task is truly done. It must fail before work starts.
Self-test
Proof that the grader fails on a wrong stub and passes on a correct one.
Write set
The files a worker is allowed to change. Touching anything else is a deviation.
Verdict sheet
Collect-Row's printout: one PASS/FAIL line per check.
Verifier
A fresh agent that re-checks the work from the ticket alone and assumes it's broken.
Residual
At close: "none", or the key of an existing row that carries what's left.
Deviation
note passes and gets logged. blocked means the ticket was wrong: fix it, no failure counted. scope means the worker overstepped: fail and roll back.
Board
The schedule Artifact plus two vault pages (TaskUpdate.html and the section plan), all rebuilt by the scripts.
Ledger
.foreman\ledger.md, a generated view of the row records. Never edited by hand.
Gate
A stop point. Only your approval, via Approve-Gate.ps1, lets the rows after it run.
