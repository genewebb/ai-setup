# TestAuto Test Data Generation

> **Scope**: speed-merchants (TestAuto.Shared + scenario projects)
> **Source**: `TestAuto/Documentation/TestDataGeneration.md`

Test records are generated by `TestDataFactory`, which selects the generator based on the `TestDataType` declared in a scenario's `[ScenarioTypes]` attribute. Each scenario gets one generator class, which determines whether records are produced in pages or one at a time.

---

## Key Configuration Parameters

| Parameter | Location | Purpose |
|---|---|---|
| `RecordsPerBatch` | `ScenarioRuntime` | Page size for paged generators |
| `BatchSize` | `ScenarioRuntime` | Fallback if `RecordsPerBatch` absent |
| `TestRecordLimit` | `ScenarioTesting` | Cap on total records across all batches |

## What `TestDataFactory` actually emits per `DataPattern`

`TestAuto.Scenarios\Factories\TestDataFactory.cs` → `GetRecordsForScenario(scenario,
scenarioConfiguration, numberOfGeneratedTestRecordsPerBatch, pageSize, pageNumber)`. It reads
`ScenarioTypesAttribute` off the scenario type (throws `InvalidOperationException` if absent),
`Activator.CreateInstance`s the `TestDataType`, calls `generator.Initialize(scenarioConfiguration)`
— and then branches on `attr.DataPattern` (`TestDataFactory.cs:81-129`). Verified 2026-07-27 @
4c367fe6; re-read the switch if counts look wrong.

| `DataPattern` | What the factory returns | Is `GetRecords` called? |
|---|---|---|
| `Single` (`:83-92`) | `generator.GetRecords(pageNumber, numberOfGeneratedTestRecordsPerBatch)`, `.ToList()`, null → empty | **Yes** |
| `Paged` (`:94-119`) | N **synthetic envelope records** — see below | **NO** |
| anything else (`Other`, `SelfManaged`) (`:121-128`) | `generator.GetRecords(pageNumber, pageSize)` — note `pageSize`, not the per-batch count | **Yes** |

Short-circuit ahead of all of it: if `scenarioConfiguration.ScenarioName == "DefaultScenario"` the
method returns an empty list immediately (`TestDataFactory.cs:58`), before the null/range argument
guards and before the generator is ever constructed.

### ⚠️ `DataPattern.Paged` — the envelope factory (the generator is NOT used)

This is the single most misleading part of the pipeline. For `Paged`, the declared `TestDataType`
is still instantiated and `Initialize`d, but **`GetRecords` is never invoked and no test records
are produced**. Instead the factory hand-builds `N = numberOfGeneratedTestRecordsPerBatch` blank
"envelope" records, each carrying only two number attributes:

```csharp
// TestDataFactory.cs:104-111
result = new List<Record>(capacity: envelopes);
for (int i = 0; i < envelopes; i++)
{
    var env = DataRecordBase.BlankRecord();
    env.AddNumberAttribute(MetadataConstants.AttributePageNumber, pageNumber + i);  // page walks per envelope
    env.AddNumberAttribute(MetadataConstants.AttributeBatchSize,  pageSize);        // same for all
    result.Add(env);
}
```

Consequences worth internalising:

- An envelope is a **work ticket**, not data. One envelope ⇒ one Hangfire job ⇒ that job fetches or
  generates page `pageNumber + i` of `pageSize` records itself. This matches the `DataPattern.Paged`
  XML doc: *"One Hangfire job per page/batch"* (`TestAuto.Shared\Common\Scenario\ScenarioTypesAttribute.cs:12-15`).
- `numberOfGeneratedTestRecordsPerBatch` controls **how many pages are dispatched**, and `pageSize`
  controls **how big each page is** — they are not "records per batch" and "page size" in the naive
  sense. `envelopes` is floored at 1 (`:97-98`).
- Declaring `typeof(PagedRecords)` on a `Paged` scenario is effectively **decorative**. Writing a
  custom generator and pairing it with `DataPattern.Paged` produces nothing; pair a custom
  generator with `Single` (or a non-`Single`/non-`Paged` pattern) instead.
- `TestRecordLimit` is not consulted anywhere in this method.
- The envelope attribute names come from `MetadataConstants.AttributePageNumber` /
  `MetadataConstants.AttributeBatchSize` — the same pair the real `PagedRecords`,
  `PagedRecordsReverseOrder`, `PagedRecordsRandom` and `StewardshipRecordGenerator` stamp onto
  records, which is why downstream code cannot tell an envelope from a record by shape alone.
  `DataRecordBase.BlankRecord()` seeds both to `0` (`TestAuto.Shared\Helpers\DataRecordBase.cs:91-92`)
  before the factory overwrites them.

### `DataPattern.Single`

- The factory **honors the requested per-batch count N** — it calls
  `generator.GetRecords(pageNumber, N)` (comment: *"Honor N fully (no Take(1))"*,
  `TestDataFactory.cs:85-86`), returning all N per batch. The old cap of exactly one record per
  batch (the `Take(1)`) has been **removed**.
- Per the enum's own doc comment, `Single` means "one Hangfire job per record", not "one record".
- Any per-generator `TestRecordLimit` capping happens **inside** the generator, not in the factory.

## Declaring a Generator on a Scenario

The TestDataType is set in the `[ScenarioTypes]` attribute (first parameter):

```csharp
[ScenarioTypes(
    typeof(PagedRecords),              // ← TestDataType
    typeof(MyMetricDetail),
    typeof(MetricBatchSummaryBase),
    RestSubjectArea.Profisee,
    DataPattern.Paged
)]
public class MyScenario : ScenarioBaseCrud { }
```

Use `ScenarioConfigurationOnly` (config-driven, no records) or `DefaultNoOpGenerator` (no-op) when the scenario drives its own data and doesn't need the factory:

```csharp
[ScenarioTypes(typeof(ScenarioConfigurationOnly), ...)]
```

## Adding a Custom Generator

Add a generator in `TestAuto.Shared/DataRecordGenerators/`. **There is no registration, no lookup, and no assembly scanning** — `TestDataFactory` selects the generator *solely* from the `typeof(...)` `TestDataType` in a scenario's `[ScenarioTypes]` attribute and instantiates it via `Activator.CreateInstance(testDataType, _configuration, _serviceProvider)`. The class therefore **must** expose a public `(IConfiguration, IServiceProvider)` constructor — normally by inheriting `DataRecordBase` (which implements `ITestData` and provides that ctor). A plain parameterless `ITestData` throws `MissingMethodException`.

```csharp
public class MyCustomGenerator : DataRecordBase   // supplies the (IConfiguration, IServiceProvider) ctor + ITestData
{
    public MyCustomGenerator(IConfiguration configuration, IServiceProvider serviceProvider)
        : base(configuration, serviceProvider) { }

    public override List<Record> GetRecords(int pageNumber, int pageSize)
    {
        // return records for this page
    }
}
```

To use it, point a scenario's `[ScenarioTypes]` at it (`typeof(MyCustomGenerator)`) — that `typeof` **is** the selection mechanism. No DI wiring or factory edit is required.

> ⚠️ …**unless the scenario's `DataPattern` is `Paged`**, in which case `GetRecords` is never
> called and your generator's output is discarded in favour of synthetic envelopes (see "What
> `TestDataFactory` actually emits per `DataPattern`" above). If your generator must produce the
> records, do not declare `DataPattern.Paged`.

## TestData.CloneAndMutate (standalone console tool) — Mutation Rule Configuration

> ⚠️ **Scope: this section describes the STANDALONE `TestData.CloneAndMutate` console tool
> (`TestData.CloneAndMutate\Mutation\Mutation.md`), NOT `CloneAndMutateScenario`.** The rule
> numbers below (2=SlightTypo, 4=MutateAddress/DOB/SSN, 5=MutateCity, … 11=MutatePhone, plus the
> `Swap{Position,Count}` config) are this console tool's vocabulary and do **not** drive the
> scenario. `CloneAndMutateScenario` runs through `VariantGenerator.GenerateAttributeVariants`
> (`CloneAndMutateScenario.cs:171`) whose `ApplyRule` (`VariantGenerator.cs:223-232`) uses a
> **different** vocabulary: `0`=unchanged, `1`=blank, `2`=no-op, `3`=`SwapCharacters` (2-arg, no
> Position/Count), `4`=`SlightTypo`, `5`=synonym swap, `6+`=no-op. See
> **testauto-record-transformation → "VariantGenerator"** for the scenario's actual rules before
> editing any scenario `DataMutationSettings`.

The standalone console tool varies cloned records using `MutationSettings:RuleDefinitions` in `appsettings.json`. Each attribute selects **exactly one** mutation rule at random, controlled by weights.

### Rule Number → Behavior

**Canonical source: `TestData.CloneAndMutate\Mutation\RuleIds.cs`** (the file's own comment: *"Keep
this in sync with the switch in MutationTransformer"*). Ids read from live code 2026-07-27 @
4c367fe6 — re-read `RuleIds.cs` and `Mutation\MutationHelper.cs` rather than trusting this copy.
There are **14** ids (0–13), not 12. For the full behavioural write-up (regex format-preservation,
weighted selection, `Convert.ChangeType` nulling) see [[testdata-enrichment-pipeline]], which owns
this subsystem.

| Rule # | `RuleIds` const | Effect |
|-------:|---|---|
| **0** | `NoChange` | leave value as-is |
| **1** | `Blank` | return empty string |
| **2** | `Typo` | `SlightTypo` — swap adjacent / delete / duplicate one char |
| **3** | `Swap` | `SwapCharacters` — reverse `Swap.Count` chars at `Swap.Position` |
| **4** | `Address` | `MutateAddress` — tweak a digit in the leading house number, else `SlightTypo` |
| **5** | `City` | `MutateCity` — `SlightTypo` on the trimmed value |
| **6** | `CaseToggle` | toggle case of one random letter |
| **7** | `State` | 2-letter code → replace one letter; otherwise `SlightTypo` |
| **8** | `Country` | normalize to a random US variant ("United States" / "USA" / "United States of America") |
| **9** | `Postal` | `MutatePostal` — mutate one digit (ZIP-aware) |
| **10** | `Email` | `MutateEmail` — plus-alias, or typo in local/domain part |
| **11** | `Phone` | `MutatePhone` — replace **exactly one** digit, formatting chars preserved |
| **12** | `DOBShift` | `MutateDOB` — shift date ±1–5 days, returns `yyyy-MM-dd` |
| **13** | `SSNMutate` | `MutateSSN` — tweak one digit, hyphens preserved |

> 🚫 **Corrections vs the older table that used to live here (and vs the repo's `Mutation.md`,
> which is stale in the same way):** rule 4 is address-only — DOB and SSN are their **own** ids
> (12, 13), not folded into 4. Rule 5 is a typo pass, not "change case or remove spaces". Rule 7
> replaces a letter, it does not toggle full-name ↔ abbreviation. Rule 8 normalises to a random US
> variant rather than toggling a pair. Rule 11 replaces one digit, not every digit.

### Rule Definition JSON Shape

```jsonc
"MutationSettings": {
  "RuleDefinitions": {
    "FirstName": {
      "Rules":   [1, 2, 3],
      "Weights": [0.3, 0.3, 0.4],
      "ApplyMoreThanASingleRule": false,
      "Swap": { "Position": "Middle", "Count": 2 }
    },
    "DateOfBirth": {
      "Rules":   [0, 4],
      "Weights": [0.85, 0.15],
      "ApplyMoreThanASingleRule": false
    },
    "FullName": {
      "Rules":   [0],
      "Weights": [1.0],
      "ApplyMoreThanASingleRule": false
    }
  },
  "AttributeGroups": {
    "NameGroup": ["FirstName", "LastName"]
  }
}
```

### Swap Rule Detail (Rule 3)

The enum is `SwapPositionOptions.SwapPosition`
(`MutationHelper.SwapCharacters(string?, SwapPositionOptions.SwapPosition, int)`,
`TestData.CloneAndMutate\Mutation\MutationHelper.cs:100-109`). The first member is
**`Beginning`**, not `Start`:

| Position | Effect |
|---|---|
| `Beginning` | Reverse the first `Count` characters |
| `Middle` | Reverse `Count` characters centered in the string |
| `End` | Reverse the last `Count` characters |

### `ApplyMoreThanASingleRule` — present on the model, never read

- **Exactly one rule fires per attribute per record**, regardless of this flag.
  `MutationRuleDefinition.ApplyMoreThanASingleRule` exists (and appears in `appsettings.json` and
  the repo's `Mutation.md`), but `TestData.CloneAndMutate\Mutation\MutationTransformer.cs` never
  reads it. Setting it to `true` is a no-op. Same for `MutationSettings.AttributeGroups`, which
  `Mutation.md:88` itself flags as unimplemented in the console tool.

### Tuning Guidance

| Goal | Action |
|---|---|
| More blank-outs | Increase weight next to rule `1`; decrease `0` weight |
| No mutation on an attribute | Set `Rules: [0], Weights: [1.0]` |
| Stress fuzzy scoring | High weights on rules 2, 3, 4 for matching attributes |
| DOB / SSN variation | Use rules `12` / `13` — **not** rule `4` |

> Weighted selection detail: `roll = rng.NextDouble() * sum(Weights)`, accumulate until
> `roll <= acc`; falls back to the **last** rule id if nothing matches, and returns the value
> unchanged when `Rules`/`Weights` are null, empty, count-mismatched, or total weight ≤ 0.

> Use `"TestMode": true` with a small `TestRecordLimit` to sample mutated output before running at scale.
