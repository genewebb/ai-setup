# stream-kit

Operator guide (order, session counts, owner queue): `stream-howto.md` in this folder.

## The roles

| Skill | Session | Moves tasks | Prompts the owner |
|---|---|---|---|
| `/stream-plan` | on demand | creates `planned` tasks (or `ticketed` on import) | yes, the only one |
| `/loop /stream-author` | 1..N | `planned` -> `ticketed` | no |
| `/loop /stream-build` | 1..N | `ticketed` -> `building` -> `built` | no |
| `/loop /stream-integrate` | exactly 1 | `built` -> `integrated` -> `done`, fix tasks, group close | no (gates arrive as a command) |
| `/loop 15m /stream-status` | 1 | breaks stale claims only | no |
| `/loop 10m /stream-kit inbox` | 1 | none: works the kit inbox (script and contract bugs) every 10 min | no |
| `/loop 20m /stream-coordinator` | 1 | none of its own: works the kit inbox, stands in for plan when no planner is live, salvages stalled work, fixes kit-caused stalls | only owner-only decisions (a notification) |
| `/stream-adhoc` (`addStreamTab -Role Adhoc`) | 0..1, interactive | none: carries one owner request from requirement to commit, in closed groups only; future-group work goes to stream-plan as a requirement plus an inbox item | yes: requirement and mockup approval, every decision |

The flow for each group:
1. The plan releases the group.
2. Authors ticket its tasks while builders build the ones already ticketed.
3. The integrator applies each verified patch to the dirty main tree as soon as it is built.
4. When the whole group is integrated, the integrator runs the suites once, then fix tasks, then one more run.
5. The group closes when that run is green and its gates have passed.

stream-integrate commits each patch once its grader passes on main. The one other committer is stream-adhoc, and only
through `Commit-AdhocChange.ps1`, which holds the integrator's drain lock and the main-tree lock from apply to commit.
Nothing branches, and only stream-adhoc removes a worktree (its own, on the owner's yes).

## Starting a repo

1. `/stream-plan` with a start prompt that names the repo, the requirements and the groups. It releases the tasks straight away (no approval step).
2. Open the sessions: at least one author and one builder, one integrator, one status and one coordinator. Pre-approve the kit's shell commands for every session: a session waiting on an approval prompt looks dead.
3. Preferred (owner rulings 2026-10-04): authors and builders run as **fresh-context runners**, one new session per ticket or build. Planner, integrator, kit, coordinator and status run as **one long interactive session each** under their `/loop`, so the owner can work with them, with the `stream-compact` mod (`mods\stream-compact`, `--plugin-dir`) compacting the session after a turn once context fill reaches `STREAM_COMPACT_PCT` (35). The owner's pwsh profile opens both kinds (`addStreams`, `addStreamTab`). A runner can still run any role: `pwsh -NoProfile -File "{ClaudeHome}\skills\stream-kit\scripts\Start-StreamRunner.ps1" -Repo {SpeedyRepo} -Role <role>` once per session in its own terminal. `<role>` is author, build, integrate, plan, status, kit or coordinator.
   - Each unit of work runs in a new Claude session: one ticket, one build, or one timed review.
   - Three launch modes. Default: a headless `claude -p` session, its JSON result logged when it ends; its last line `UNIT-OUTCOME: <outcome>` stands in for `unit_done` (lib `Get-UnitOutcome`), so an `idle` headless unit backs a timed runner off too. `-Stream`: the
     same `-p` session with a live text feed in the runner's tab (one line per message and tool call). `-Live`
     (recommended for watching): an interactive session in the runner's own tab with Remote Control on, so the unit
     shows live in the terminal and in claude.ai/code or the Claude app under its session id. The `stream-unit` mod
     (`mods\stream-unit`, loaded with `--plugin-dir`) gives it the `unit_done` tool; the skill's last call writes the
     unit's result file and the session exits. A `-Live` unit past its wall-clock limit (`-UnitTimeoutSeconds`,
     default author 1800, build 5400, others 1200) is ended and logged `TIMEOUT`; it counts as a failed run only when it wrote no result. A unit still at the prompt 120 s (`-ResultGraceSeconds`) after it wrote its result is ended as an ok run (`RESULT-GRACE`).
   - The runner checks the machine configuration through the `ai` launcher (`ai.ps1 --version`) when it starts and
     every 60 minutes after (`-LaunchCheckMinutes`), then starts each session directly with the environment `ai`
     sets. That check took 111 s on SMVMTR1, so running it once per unit cost about two minutes each.
   - **Pre-staged units (2026-10-06, prestage-runner-design).** An author or build runner does the unit's plumbing
     itself before Claude starts: it takes the oldest actionable inbox item in the unit's name or claims the next
     row (`Claim-Task.ps1`, the gate's own selector); for a build it lays the worktree, proves the author grader
     RED (a not-red row bounces to `planned` with no launch), restores a kept patch and grades it; then it writes
     `.streams\units\<session>\{task.json,unit.md}` and launches with `packet: <unit.md>`. An idle gated runner
     watches `tasks.json` and its inbox file (a stat every 5 s) instead of sleeping. A build unit that dies holding
     its claim has its worktree exported to the row's patch before the claim is released. `-NoPreStage` keeps the
     old behaviour for a comparison run.
   - **The owner sets the focus and the models in `.streams\config.json`** (written with empty fields by the first
     runner that finds it missing). `focus.groups` names the group(s) every work role is offered rows from, e.g.
     `["G4"]` or `["G4", "G6"]`, read in board order; empty = the first unclosed group. Authors have their own queue
     (owner ruling 2026-10-12): with no planned focus row they SPILL into the other released groups' planned rows
     (group order, then ready-first), stamping the main commit in the row's `spill` field; builders and the integrator
     never spill, and a spill ticket whose write-set files moved by the time its group is focus reads `STALE-TICKET`
     on the board and at the build claim. `defaults` and `roles.<role>`
     set `model`, `subagentModel`, `effort` and `promptCacheTtl`; the runner reads the file before every unit
     (`-Model` on the runner line overrides the model). An edit takes effect at the next unit; `Start-StreamRunner.ps1
     -DryRun` prints the `FOCUS` and `CONFIG` it would use.
   - Each role keeps lessons for its next units in `.streams\lessons\<role>.md` (`Add-Lesson.ps1`); every runner
     session reads its role's file before it takes work, and the coordinator prunes it.
   - Author and build runners launch only when the gate finds something to take; otherwise they sleep at no token cost.
   - Timed runners launch once per interval: integrate, plan and kit every 600 s, status every 900 s, coordinator every 1200 s.
   - One planner at a time: a plan launch waits one interval (`LIVE-PLANNER <session>`) while another `plan*` session wrote task history, or took or closed a `stream-plan` item, inside 30 minutes (the coordinator's liveness rule).
   - Stop one role with `.streams\runners\STOP-<role>`, or every runner with `.streams\runners\STOP`. The runner checks between sessions, so a live session is never killed.
   - Runner state is in `.streams\runners\<runner>.json`, and one JSON result per session is in `.streams\logs\runner\`.

|---|---|---|
| `Init-Streams.ps1 -Repo` | plan | Creates `.streams\` (with the six role inboxes) and adds it to `.git\info\exclude`. Idempotent. |
| `Add-Tasks.ps1 -Repo -Role plan\|integrate -Session -File` | plan, integrate | Adds groups and tasks from JSON. Refuses a missing why, a missing write set, overlapping write sets, or an integration task that dependsOn a LATER group's row (`LATER-GROUP-DEP`: groups close in board order, owner ruling 5979). An integration fix on a not-yet-landed task's file joins that task; on an integrated task's file it is chained after it (`CHAINED`); a fix to a group whose integration task is `done` reopens it (`REOPENED`). |
| `Claim-Task.ps1 -Repo -Role author\|build -Session [-Task <id>]` | author, build | Atomic claim: integration fix tasks first (they hold a group's close), then the group's order, then the critical path. For an AUTHOR claim the group is the row's EFFECTIVE group, the earliest group among the row and every row that depends on it (`Get-EffectiveGroupRank`), so a later-group root that holds earlier-group tickets is authored with that earlier group. Inside the effective group the author sort always puts a ready row first (every dependency built or later, so its ticket is claimable on release), then the chain; the build sort keeps each row's own group. Prints the task as JSON, or `NONE` (and then leaves the session's idle beat; a claim removes it). `-Task` claims exactly that row, skipping the sort but applying the same gates, and refuses with `REFUSED-TASK <id> : <gate>` and exit 2. The sort SKIPS a row named by a live `taken` inbox item (its task field, or an ask that LEADS with `<id>:`), because its artifacts are being rewritten; the skip is printed as a warning and `-Task` overrides it. | `Update-Task.ps1 -Repo -Task -Role -Session [-To] [-Note] [-Artifacts] [-Base] [-AddWriteSet] [-Beat] [-Release]` | all | The one way to change a task. `-AddWriteSet` (build only) is the auto-accepted widening of the builder's own write set, logged to `decisions.md`. Exit 3 = `CLAIM-LOST`, exit 6 = `TRANSITION-REFUSED`, exit 7 = `WRITESET-OVERLAP`. `-To integrated` from `blocked` (integrate role) records a verified patch already on main, and is refused unless the kept patch reverse-applies clean on the main tree. | `Remove-TaskWorktree.ps1 -Repo -Session (-Task or -Path) [-BuildOutputOnly] [-Label] [-Reason]` | status, coordinator | Releases a worktree and writes the `owner\worktrees.md` line. Refuses while the task holds a live BUILD claim. `-BuildOutputOnly` keeps the tree and deletes only `bin` and `obj` that sit BESIDE a project file: matching the name alone also hit a package's own executables (9 such directories under `tests\Tests.E2E\node_modules`, so a pruned tree failed Playwright on a missing binary), and a directory a compiler holds open is reported as kept, never as a failure. |
| `Export-TaskPatch.ps1 -Repo -Task -Worktree` | build, coordinator (salvage) | Saves the patch (new, changed and deleted files). Exit 2 lists `OUTSIDE` files that are not in the write set. |
| `Invoke-Grader.ps1 -Repo -Task -Root [-Label] [-Only grader\|check] [-ExpectRed] [-TimeoutSeconds]` | build, integrate | Runs the row's builder CHECK (`artifacts.check`: clause tests plus impact tests) and its author GRADER (`artifacts.grader`, optional since 2026-10-02) into one log, check first, failing when either fails; the identity line reads `<check>+<grader>`. `-Only` runs one of them (the builder's RED before any edit is `-Only grader`); `NO-GRADER` (exit 4) when neither exists. It runs the scripts with `STREAM_TASK` and `STREAM_SINCE_UTC` set, logs the output and ends the log with `GRADER sha <hash> since <t>`. With `-ExpectRed` it is the RED check. A run against the main tree holds `.streams\main-grader.lock` (one main build at a time); exit 5 = `MAIN-GRADER-BUSY`. A beating run (`-BeatSession`) has a wall-clock limit, `-TimeoutSeconds` (`STREAM_GRADER_TIMEOUT_SECONDS`, else 3600): past it the grader's process tree is ended and the run is `GRADER-TIMEOUT`, exit 8, never RED; `Integrate-Patch.ps1` treats it as an environment failure (`RETRY`). Its child runs `-NonInteractive` with stdin read from an empty file, so a prompt for input cannot wait for ever (G4.T131 sat 2.4 h on a hung `npx` child while its beat kept the claim fresh). |
| `Test-GraderPortability.ps1 -Grader` | plan (import), author | Flags a grader (and the grader a shim calls) that compares file times, reads MyLoop row state, leaves `-Since` unset, pins a commit id or reads git history (`COMMIT-PIN`), names an absolute path under `.loop` (`OUTSIDE-TREE`), delegates to an absolute `.ps1` that is not there (`DEAD-DELEGATE`), or splits a trx `testName` on `(` without trimming it (`UNTRIMMED-TESTNAME`). Exit 0 = `PORTABLE`. |
| `Restore-TaskPatch.ps1 -Repo -Task -Worktree` | build | Lays a bounced task's kept patch on a fresh worktree: `APPLIED` (0), `NO-PRIOR` (1), `CONFLICT` (2, nothing written). |
| `New-SuiteSnapshot.ps1 -Repo -Session -Group -Run [-CopyIgnored <files>] [-Log]` | integrate | Lays down `suite-<group>-<run>`, a detached worktree of the main tree as a builder sees it (HEAD + dirty diff + untracked files, plus the named ignored files such as `.env`), for one step-B run. It holds `main-grader.lock` ONLY while it reads main, never for the run, so author RED re-runs and applies go on while a suite runs. Prints and logs `SNAPSHOT <path> HEAD <sha> ...` so failures are attributed against that sha. The `.streams` input folders are copied file by file (lib `Copy-TreeTolerant`). That copy skips writer temp files (`*.tmp.<pid>.<hex>`) and any file that disappears mid-copy, because authors write those folders while the copy runs (kit item IN-20261010211022-8ba5). Exit 5 = `MAIN-GRADER-BUSY`. The watchdog keeps the newest ready snapshot while its session holds a live integrator lock and reaps every other one. |
| `Invoke-IntegratorRun.ps1 -Repo -Session -Log -Command [-WorkDir]` | integrate | Runs one long step-B command (build, suite) in a child process (in `-WorkDir`, the suite snapshot, when given) with its output in `-Log`, beating `integrator.lock` every 30 s so the watchdog never breaks a live run; exits with the command's code, `LOCK-LOST` (5) when another session holds the lock. The watchdog also skips the orphan reset for an integration row the live lock holder set building. |
| `Enter-Integrator.ps1 -Repo -Session` | integrate | Takes or refreshes the single-integrator lock. Exit 5 = held by another session. |
| `Commit-AdhocChange.ps1 -Repo -Session -Id ADHOC-<yyyyMMdd>-<n> -Worktree -Title -TestProject -TestFilter [-Solution] [-WaitSeconds 1800] [-NoCommit]` | adhoc | Lands one ad-hoc change: exports the worktree's change to `.streams\adhoc\<Id>.patch`, waits for `integrate-patch.lock` then `main-grader.lock`, applies it to main, builds the solution and runs `dotnet test <TestProject> --no-build --filter <TestFilter>`. PASS commits exactly the patch's paths as `<Id>: <Title>` and pushes like Integrate-Patch (git policy rows, fail closed); a red build or test, or a filter that matches no test, reverses it. Outputs `COMMITTED`, `REVERSED` (exit 1), `NOTHING` (2), `REBASE` / `DIRTY` (3), `ADHOC-BUSY` (4). `STREAM_ADHOC_DOTNET` replaces dotnet (self-test). |
| `Integrate-Patch.ps1 -Repo -Session [-Task] [-NoCommit]` | integrate | Applies the next patch in dependency order, then outputs `INTEGRATED` + `COMMITTED`, `REBASE`, `SUSPECT` (grader defect: task to `planned`, patch kept), `RETRY` (build/IO environment failure on main: task stays `built`, `ticketed` after 3; or any throw after the apply, such as a state write that timed out on the tasks.json lock: the patch is reversed and the task stays `built`), `REVERSED` or `NONE`. Its tasks.json writes wait 90 s for the lock (`STREAM_TASKS_LOCK_WAIT_SECONDS`, 15 s elsewhere). One run per repo: a second concurrent run (even under the same session) prints `DRAIN-BUSY`, exit 4, and does nothing. `NOT-FOCUS <id>` for a built row outside the focus set: it stays built until its group is focus. |
| `Invoke-Watchdog.ps1 -Repo -Session` | status | Breaks stale claims, the integrator lock and dead inbox holds; reaps worktrees, exporting and attaching a patch first for any task that has not landed and KEEPING a tree whose work cannot become a patch; sweeps stale `tmp*.tmp` and `speedy-*` entries out of the host temp folder (`STREAM_TEMP_ROOT` overrides it, and a self-test must set it to its own scratch). It also sweeps every path `git worktree list` REGISTERS, not just the directories under the roots tasks recorded, so a tree an author or verifier made by hand elsewhere is seen; it sweeps that path itself and never its parent as a root, because a sibling folder there belongs to nobody on this board. Build output (`bin` and `obj` only) is pruned ONLY while the drive is at `warn` or `low` against `Get-DiskNeedMB`, never on every sweep: a `built` tree is waiting for an integrator, and a rebuild costs the next session minutes it pays for nothing while C: has room. A prune keeps the tree and its source, and its `owner\worktrees.md` line names the band and the free space that caused it. Prints one line per action or `QUIET`, then any `JUNK` / `WARN` note. |
| `Get-StreamStatus.ps1 -Repo [-Json]` | status | Read-only 6-line summary (with open inbox counts), or the page model. Each role's live sessions split into working (holding a claim) and idle: a claim that comes back `NONE` writes an idle beat to `.streams\idle\<session>.json` and a claim clears it, so an idle poller counts as live inside its role's limit. A live session with no claim that wrote nothing for over 20 minutes counts as `quiet`, not idle: it has stopped claiming. Quiet builders beside claimable rows raise a flag that names them. Beside the build sessions it counts the CLAIMABLE ticketed rows, using `Claim-Task.ps1`'s own gates (released group, no live claim, no live inbox hold, `Test-BuildReady`). The model's `authorRank` lists each planned row that inherits an earlier group, with the row it comes through (`via`). Below the claimable buffer (2 claimable rows per live builder) it raises `PIPELINE DRY: claimable N of target M` with the dominant reason (no author live, RED queue, waiting on unticketed dependency, authors behind, nothing ready), and the page marks the tile. It flags `main tree held <n> min by '<holder>'` when one holder keeps `main-grader.lock` past 20 minutes, and the model's `releases` (shown beside the claimable tile) counts author releases (planned to ticketed) per hour for the last 6 h. When rows are ticketed but none is claimable, a flag names the root rows the waiting chains bottom out on, and what each root needs (`needs author`, `owner gate`, ...). The claimable tile names the focus group; `PIPELINE DRY` gains the reason `focus group <G> exhausted`. The tasks line ends `left to plan N of M clauses (K in no group)`, the model's `leftToPlan`: acceptance clauses (`- id: AC-...` under `acceptance:`) of READY requirement files under `<repo>\docs\requirements` (found from the repo root first) that no row names in its why, title, tests or ticket and no COMMITTED stream-adhoc request names (`.streams\adhoc\<Id>.md` with a `<Id>:` commit on HEAD; kit item IN-20261012012612-8ef6), per group by `scope.include` plus a no-group count. A retired row is its own bucket, `retired`, carved out of `done` like `ticketing` out of `planned`: never blocked, never landed (it feeds no delivery rate, no category total, no uncommitted list), and the clauses it names count as left to plan unless another row names them. It reads `unknown: <reason>` instead of a number when a closed group has a clause no row names (the match is then untrustworthy), the folder is missing, or a READY acceptance list cannot be parsed. |

| `Revise-Task.ps1 -Repo -Session (-File <batch.json> \| -Task [-AddWriteSet] [-RemoveWriteSet] [-AddDependsOn] [-RemoveDependsOn] [-Title] [-Release auto\|planned\|ticketed\|keep\|block] [-Note])` | plan, coordinator | Revises released tasks as one batch under the lock and releases blocked ones. | `Start-StreamRunner.ps1 -Repo -Role author\|build\|integrate\|plan\|status\|kit\|coordinator [-Live \| -Stream] [-IntervalSeconds] [-UnitTimeoutSeconds] [-ResultGraceSeconds] [-LaunchCheckMinutes] [-Model] [-MaxRuns] [-Tab <name>] [-DryRun]` | owner | Fresh-context runner. `-Tab` records the terminal tab it runs in (state file `tab`) and makes it also stop, alone, on `STOP-tab-<tab>` or `STOP-<runner id>` (non-alphanumeric runs become `_`), deleting that file as it exits. It runs a role as a series of new Claude sessions, one per unit of work, with bypassPermissions (and `--permission-prompts none` under `-p`). Default mode is headless `claude -p`; `-Stream` adds `--output-format stream-json --verbose` and prints one line per message and tool call (raw events kept in a `.jsonl`); `-Live` runs an interactive session in the runner's own console with `--remote-control <session>`, `--plugin-dir mods\stream-unit` and the command as its starting prompt, reads the mod's result file (`STREAM_UNIT_OUT`) as the unit result, logs `NO-RESULT` for a session that exited without `unit_done`, and ends a session past `-UnitTimeoutSeconds` with everything it started (`TIMEOUT`), or one still running `-ResultGraceSeconds` (120) after its result file landed (`RESULT-GRACE`, an ok run: its `/exit` was swallowed by a later background-task notice). Each `-Live` unit gets its own transcript id (`--session-id <uuid>`), and the runner reads that transcript every `STREAM_RUNNER_QUOTA_CHECK_SECONDS` (10). When it sees the account's usage-limit rejection (`quotaLimits.status` `rejected`), it ends the unit at once (`USAGE-LIMIT`, never a failed run, so no backoff). It then writes `.streams\runners\quota-hold.json`, which holds the stated reset plus 30 to 150 s of jitter, at most `STREAM_RUNNER_QUOTA_MAX_WAIT_SECONDS` (21600). Every runner of the repo then waits on that hold (`QUOTA-HOLD until <t>`) and launches nothing; before this change, four author units sat idle at their prompts to `TIMEOUT` and then took a 1800 s backoff (kit item IN-20261010205318-5308). Time on an open permission prompt (the mod's `<result>.waiting.json` says waiting) does not count toward the limit: the runner retitles its block or tab `<tab> - NEEDS YOU` (Wave: `wsh setmeta frame:title` plus a bell badge; WezTerm: `set-tab-title`), sets its state to `waiting on owner`, files one `ESCALATE` line in `owner\questions.md` and re-writes it `RESOLVED` once answered, and beats every claim the unit session holds (every `STREAM_BEAT_SECONDS`, 60) so the watchdog does not break it while the owner owes an answer. The unit sees `STREAM_UNIT_TAB`. When a WORK unit (author, build) ends while it still holds an inbox item, the runner re-opens the item at once (the by column reads `RUNNER RE-OPEN, unit <session> ended <code>`) and appends `inbox\evidence\<id>.progress.md`, naming the work files the unit changed under `.streams\` and its last beat note, so the next holder continues instead of restarting; a timed role keeps its session across units and keeps its items. The unit's rules give its wall-clock limit and tell it to split work that will not fit into continuation items and to say in every beat note what is DONE. After every `-Live` unit the runner restores the console's input/output modes and resets terminal modes (alternate screen, cursor, mouse, bracketed paste, keyboard protocols), so a killed session never leaves the tab dead. The machine config is checked through the `ai` launcher (`ai.ps1 --version`, which applies a changed install) at start and once `-LaunchCheckMinutes` (60) have passed, and each session starts directly with the environment `ai` sets (CLAUDE_CODE_TMPDIR, AI_LAUNCH_REVISION, the installed AI_* env); an invalid machine config (ai exit 2) is a failed launch (`LAUNCH-CHECK REFUSED`). ## Inboxes

Every role has an inbox, `<repo>\.streams\inbox\<skill>.md`. The six are `stream-plan`, `stream-author`,
`stream-build`, `stream-integrate`, `stream-status` and `stream-kit`. Evidence files go in `.streams\inbox\evidence\`.
- Any session or the owner files work or a bug for another role with `Send-InboxItem.ps1`.
- Guidance meant for the future holder of a named row goes into THAT ROW with `Update-Task.ps1 -Note`, never into an inbox. The inbox delivers one way - a role takes an open item - so a request that only a later holder can act on waits in the wrong place: on 2026-09-30 three such items were closed by hand, one 498 minutes old, and one request was filed five times before its sender folded the substance into the row. Reserve an inbox for work a role can take now.
- A request to work ONE NAMED ROW is now deliverable, which it was not before 2026-09-30 21:5xZ: `Claim-Task.ps1 -Task <id>` claims that row when it passes the same gates the sort applies, so "ticket this one next" can be finished rather than only agreed to (kit item IN-20260930211404-3356). Two things still belong in the row instead: guidance for whoever holds it next, and anything that needs no claim.
- Each looping role works the oldest open item at the start of its cycle, within its own write rules, and forwards the
  rest.
- The contract is the header of each file (from `inbox-template.md`): append-only lines, the status is the last line,
  and every line goes through the scripts.
- The lock-checked `taken` is what stops two sessions working one item. Two authors did exactly that on 2026-09-27,
  when lines were appended by hand.
- `stream-status` counts open items per inbox and flags any that sit past their role's limit.

## `/stream-kit inbox`

The kit inbox is worked by one looping session, the kit maintainer: start it with `/loop 10m /stream-kit inbox
repo: <repo>`. Every 10 minutes it lists the open items and works each one; a tick with no open item does nothing
else. Session id (2026-10-05, priority-focus-design 3.5): the `session: <id>` in your start prompt (`<role>-<8 hex>`, chosen by the tab launcher so the cost ledger can find your transcript). Use it on every script call. Without one in the prompt, make one as before. A coordinator works this inbox too; the lock-checked `taken` line stops two sessions working one item.
1. `Get-InboxItems.ps1 -Skill stream-kit -Open`, oldest first. Take each item with `Set-InboxItem.ps1 -Status taken`.
2. Copy the live `scripts\` folder to a stage at `{ScratchRoot}\streams\<repo>\kit-<item>-stage`. Make the change there, on top of the current live files. Never
   copy an older proposal over them.
3. Run both self-tests on the stage. Both `RESULT` lines must read `fails=0`.
4. Re-read each live file and check it still matches the stage's starting copy (another session may have edited it).
   Then publish every changed file with `{ClaudeHome}\bin\Publish-KitFile.ps1 -RelativePath "skills\stream-kit\<path>"
   -Source <stage file> -BaseHash <SHA-256 of the file you staged from, or NEW>` (it writes to `{AIWorkRoot}` and
   hash-checks the write), and run `/machine-config apply`. With `-BaseHash` the publish REFUSES (`DRIFT-REFUSED`, exit
   3, nothing written) when the corpus copy is no longer your base: another session changed it, possibly with a change
   that is published but not yet installed, so the installed copy you staged from is not what you would overwrite. On
   a refusal: stop, `git merge-file` your change onto the current corpus file, re-run both suites, publish with the new
   base. Never copy over drift, even after reporting it (kit item IN-20260930210538-9dc0).
5. A change to a role's contract goes into that role's `SKILL.md` the same way, with its version bumped.
6. Close each item with `done` (what changed, and the test results) or `declined` (why).
7. Report on EVERY tick, an idle one too (owner ruling 2026-10-10). Check the kit inbox (`-Open`) and this session's
   own notifications (`ReadNotifications`). Then report: the number of open items; each item this session holds, with
   its step (staged, suites running, publishing); and what the session is working on now, or `idle`. A tick that

## Editing `scripts\` outside a kit inbox item

Steps 2 to 4 of `/stream-kit inbox` are the procedure for changing a shared script, and they bind **every** session
that writes anything under `scripts\` or into a role's `SKILL.md` — not only a session working a kit inbox item.
Stage a copy, keep the untouched live files as the base, show any new self-test case RED on the base, get
`RESULT fails=0` from both suites on the stage, re-check the live files against the base for drift, then install once.

There is no lock on that folder. A live edit is invisible to every other session until its next command fails, and
each script is step 1 of a role's cycle, so a script that throws stops all six roles at once.
