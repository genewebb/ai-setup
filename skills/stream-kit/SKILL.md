# stream-kit

Operator guide (order, session counts, owner queue): `stream-howto.md` in this folder.

## The roles

| Skill | Session | Moves tasks | Prompts the owner |
|---|---|---|---|
| `/stream-plan` | on demand | creates `planned` tasks (or `ticketed` on import) | yes, the only one |
| `/loop /stream-author` | 1..N | `planned` -> `ticketed` | no |
| `/loop /stream-build` | 1..N | `ticketed` -> `building` -> `built` | no |
| `/loop /stream-integrate` | exactly 1 | `built` -> `integrated` -> `done`, fix tasks, group close | no (gates arrive as a command) |
| `/loop 15m /stream-status` | 1 | breaks stale claims only | no |
| `/loop 10m /stream-kit inbox` | 1 | none: works the kit inbox (script and contract bugs) every 10 min | no |
| `/loop 20m /stream-coordinator` | 1 | none of its own: works the kit inbox, stands in for plan when no planner is live, salvages stalled work, fixes kit-caused stalls | only owner-only decisions (a notification) |
| `/stream-adhoc` (`addStreamTab -Role Adhoc`) | 0..1, interactive | none: carries one owner request from requirement to commit, in closed groups only; future-group work goes to stream-plan as a requirement plus an inbox item | yes: requirement and mockup approval, every decision |

The flow for each group:
1. The plan releases the group.
2. Authors ticket its tasks while builders build the ones already ticketed.
3. The integrator applies each verified patch to the dirty main tree as soon as it is built.
4. When the whole group is integrated, the integrator runs the suites once, then fix tasks, then one more run.
5. The group closes when that run is green and its gates have passed.

stream-integrate commits each patch once its grader passes on main. The one other committer is stream-adhoc, and only
through `Commit-AdhocChange.ps1`, which holds the integrator's drain lock and the main-tree lock from apply to commit.
Nothing branches, and only stream-adhoc removes a worktree (its own, on the owner's yes).

## Starting a repo

1. `/stream-plan` with a start prompt that names the repo, the requirements and the groups. It releases the tasks straight away (no approval step).
2. Open the sessions: at least one author and one builder, one integrator, one status and one coordinator. Pre-approve the kit's shell commands for every session: a session waiting on an approval prompt looks dead.
3. Preferred (owner rulings 2026-10-04 and 2026-10-17): authors, builders, the integrator, kit, coordinator and status run as **fresh-context runners**, one new session per unit. The integrator, kit and coordinator launch a unit only when the runner's script gate finds work, and status is a PowerShell tick with a Claude unit only for its own inbox, so an idle tab costs no tokens. The planner runs as **one long interactive session** under its `/loop`, so the owner can work with it, with the `stream-compact` mod (`mods\stream-compact`, `--plugin-dir`) compacting the session after a turn once context fill reaches `STREAM_COMPACT_PCT` (35). The owner's pwsh profile opens both kinds (`addStreams`, `addStreamTab`). A runner can still run any role: `pwsh -NoProfile -File "{ClaudeHome}\skills\stream-kit\scripts\Start-StreamRunner.ps1" -Repo {SpeedyRepo} -Role <role>` once per session in its own terminal. `<role>` is author, build, integrate, plan, status, kit or coordinator.
   - Each unit of work runs in a new Claude session: one ticket, one build, or one timed review.
   - Three launch modes. Default: a headless `claude -p` session, its JSON result logged when it ends; its last line `UNIT-OUTCOME: <outcome>` stands in for `unit_done` (lib `Get-UnitOutcome`), so an `idle` headless unit backs a timed runner off too. `-Stream`: the
     same `-p` session with a live text feed in the runner's tab (one line per message and tool call). `-Live`
     (recommended for watching): an interactive session in the runner's own tab, so the unit shows live in the terminal;
     add `-Remote` to also turn Remote Control on, so claude.ai/code and the Claude app list it under its session id. The `stream-unit` mod
     (`mods\stream-unit`, loaded with `--plugin-dir`) gives it the `unit_done` tool; the skill's last call writes the
     unit's result file and the session exits. A `-Live` unit past its wall-clock limit (`-UnitTimeoutSeconds`,
     default author 1800, build 5400, others 1200) is ended and logged `TIMEOUT`; it counts as a failed run only when it wrote no result. A unit still at the prompt 120 s (`-ResultGraceSeconds`) after it wrote its result is ended as an ok run (`RESULT-GRACE`).
   - The runner checks the machine configuration through the `ai` launcher (`ai.ps1 --version`) when it starts and
     every 60 minutes after (`-LaunchCheckMinutes`), then starts each session directly with the environment `ai`
     sets. That check took 111 s on SMVMTR1, so running it once per unit cost about two minutes each.
   - **Pre-staged units (2026-10-06, prestage-runner-design).** An author or build runner does the unit's plumbing
     itself before Claude starts: it takes the oldest actionable inbox item in the unit's name or claims the next
     row (`Claim-Task.ps1`, the gate's own selector); for a build it lays the worktree, proves the author grader
     RED (a not-red row bounces to `planned` with no launch), restores a kept patch and grades it; then it writes
     `.streams\units\<session>\{task.json,unit.md}` and launches with `packet: <unit.md>`. An idle gated runner
     watches `tasks.json` and its inbox file (a stat every 5 s) instead of sleeping. A build unit that dies holding
     its claim has its worktree exported to the row's patch before the claim is released. `-NoPreStage` keeps the
     old behaviour for a comparison run.
   - **The owner sets the focus and the models in `.streams\config.json`** (written with empty fields by the first
     runner that finds it missing). `focus.groups` names the group(s) every work role is offered rows from, e.g.
     `["G4"]` or `["G4", "G6"]`, read in the order written (owner ruling 2026-10-14: the written order is the priority
     order the claims, the integrator's applies and the status page follow); empty = the first unclosed group. Authors have their own queue
     (owner ruling 2026-10-12): with no planned focus row they SPILL into the other released groups' planned rows
     (group order, then ready-first), stamping the main commit in the row's `spill` field; builders and the integrator
     never spill, and a spill ticket whose write-set files moved by the time its group is focus reads `STALE-TICKET`
     on the board and at the build claim. `defaults` and `roles.<role>`
     set `model`, `subagentModel`, `effort` and `promptCacheTtl`; the runner reads the file before every unit
     (`-Model` on the runner line overrides the model). An edit takes effect at the next unit; `Start-StreamRunner.ps1
     -DryRun` prints the `FOCUS` and `CONFIG` it would use.
   - Each role keeps lessons for its next units in `.streams\lessons\<role>.md` (`Add-Lesson.ps1`); every runner
     session reads its role's file before it takes work, and the coordinator prunes it.
   - Author and build runners launch only when the gate finds something to take; otherwise they sleep at no token cost.
   - **Every role is gated (owner ruling 2026-10-17, token review: timed launches that found nothing cost about $115 a day).** integrate launches a unit only for an actionable `stream-integrate` item, a built row in the focus set (`Get-Claimable integrate`), a group `integrating`, or its own integrator lock still beating (a detached run to poll); plan and kit only for an actionable item in their inbox (plan still waits out a live planner); the coordinator (no inbox of its own: it works the kit inbox) for open plan or kit items with no live session of that role (it stands in), a change in the status page's flags, free RAM under 6 GB, its first unit after the runner started, or `STREAM_COORDINATOR_REVIEW_SECONDS` (7200) since its last unit. With nothing to take a timed runner shows the same IDLE report as a work runner and watches its inbox (integrate also `tasks.json`); the fallback re-check is still integrate 600 s, plan and kit 600 s, coordinator 1200 s.
   - **status is a script tick, no model call.** Every 900 s the runner itself runs `Invoke-Watchdog`, `Get-StreamStatus` (the terminal lines), `Build-StatusPage`, `Get-StreamCost` + `Build-CostPage`, `Build-PriorityPage`, `Archive-TaskHistory` (first tick of each UTC day, marker `.streams\runners\status-archive.day`), `Activate-Group` for a focus group without `plans\<G>.activation.json` and `Activate-Group -FreshnessOnly` for every focus group that has one (a ticketed row whose own files moved on main since it was ticketed goes back to an author now, not at the next activation), then prints ONE `STATUS-TICK` heartbeat line (the owner's "report every tick" ruling: the runner line is enough). A failed step is on that line and, once per script per runner, a `stream-kit` bug item. A step that lost a lock race (`lock busy for <n>s`, `being used by another process`) reads `BUSY` and prints `TICK-BUSY`; it is filed only after `STREAM_TICK_BUSY_REPORT` (3) busy ticks in a row (kit item IN-20261018192923-9972). A Claude unit (`/stream-status inbox`) is launched only when the `stream-status` inbox has an open item.
   - One planner at a time: a plan launch waits one interval (`LIVE-PLANNER <session>`) while another `plan*` session wrote task history, or took or closed a `stream-plan` item, inside 30 minutes (the coordinator's liveness rule).
   - Stop one role with `.streams\runners\STOP-<role>`, or every runner with `.streams\runners\STOP`. The runner checks between sessions, so a live session is never killed.
   - Runner state is in `.streams\runners\<runner>.json`, and one JSON result per session is in `.streams\logs\runner\`.

## Shared scripts (`scripts\`, PowerShell 7)

| Script | Used by | Does |
|---|---|---|
| `Init-Streams.ps1 -Repo` | plan | Creates `.streams\` (with the six role inboxes) and adds it to `.git\info\exclude`. Idempotent. |
| `Add-Tasks.ps1 -Repo -Role plan\|integrate -Session -File` | plan, integrate | Adds groups and tasks from JSON. Keeps the planner's `dependsWhy` (id -> reason) text, planner text ONLY: the mechanical classes (`shared file`, `group order`, `mockup first`) and `unstated` are derived by lib `Get-DependsWhy`, never stored, so an entry in the map always means the planner stated it (2026-10-18 dependency review F3). Refuses a missing why, a missing write set, overlapping write sets, or an integration task that dependsOn a LATER group's row (`LATER-GROUP-DEP`: groups close in board order, owner ruling 5979). An integration fix on a not-yet-landed task's file joins that task; on an integrated task's file it is chained after it (`CHAINED`); a fix to a group whose integration task is `done` reopens it (`REOPENED`). Two rows that share ONLY exact composition / registration files (lib `$script:CompositionFileRx`: `src/Composition/`, `Program.cs`, `*Module.cs`, `*ServiceCollectionExtensions.cs`, `Routes.razor`; no wildcard or directory entry) are not an overlap: ORDERED-BY-MERGE (lib `Test-MergeOrderedOverlap`, owner ruling 2026-10-18, kit item IN-20261018133755-8c9f), and `Get-BoardProblems` (so `Revise-Task.ps1` and `Test-BoardOrder.ps1`) skips those paths too. |
| `Claim-Task.ps1 -Repo -Role author\|build -Session [-Task <id>]` | author, build | Atomic claim: integration fix tasks first (they hold a group's close), then the group's order, then the critical path. For an AUTHOR claim the group is the row's EFFECTIVE group, the earliest group among the row and every row that depends on it (`Get-EffectiveGroupRank`), so a later-group root that holds earlier-group tickets is authored with that earlier group. Inside the effective group the author sort always puts a ready row first (every dependency built or later, so its ticket is claimable on release), then the chain; the build sort keeps each row's own group. Prints the task as JSON, or `NONE` (and then leaves the session's idle beat; a claim removes it). `-Task` claims exactly that row, skipping the sort but applying the same gates, and refuses with `REFUSED-TASK <id> : <gate>` and exit 2. The sort SKIPS a row named by a live `taken` inbox item (its task field, or an ask that LEADS with `<id>:`), because its artifacts are being rewritten; the skip is printed as a warning and `-Task` overrides it. Offers rows from the focus set only (`Get-Claimable`); `-Task` on a row outside it refuses `not-focus`. |
| `Update-Task.ps1 -Repo -Task -Role -Session [-To] [-Note] [-Artifacts] [-Base] [-AddWriteSet] [-Beat] [-Release]` | all | The one way to change a task. A `built` row moved anywhere but `integrated`/`done` writes a `DEP-MOVED <id> built -> <state>` history line on every `building` row whose base stacked it (`lib\Streams.ps1 Add-DependentBounceNotes`; the board flags it, and its hand-off meets `BASE-STALE` unless the dependency lands unchanged). `-AddWriteSet` (author and build; owner ruling 2026-10-17 added authors) is the auto-accepted widening of the unit's own claimed row's write set, logged to `decisions.md`. Exit 3 = `CLAIM-LOST`, exit 6 = `TRANSITION-REFUSED`, exit 7 = `WRITESET-OVERLAP`. `-To integrated` from `blocked` (integrate role) records a verified patch already on main, and is refused unless the kept patch reverse-applies clean on the main tree. An author holding a live taken `stream-author` item that names a `ticketed`, unclaimed row may set that row's `-Artifacts` (alone, no claim): stream-author step 0 rewrites such a row's grader, and nothing could record the new path (kit item IN-20261010152029-7e12); anything more is `REFUSED` (exit 2). |
| `New-TaskWorktree.ps1 -Repo -Task -Session [-WorktreeRoot]` | build | Detached worktree, with a base of HEAD + the dirty diff + untracked files + the patches of built dependencies. Records `base.deps` (`<patch leaf>:<hash>` per stacked dependency patch), which `Integrate-Patch.ps1` compares at landing (`BASE-STALE`). |
| `Remove-TaskWorktree.ps1 -Repo -Session (-Task or -Path) [-BuildOutputOnly] [-Label] [-Reason]` | status, coordinator | Releases a worktree and writes the `owner\worktrees.md` line. Refuses while the task holds a live BUILD claim. `-BuildOutputOnly` keeps the tree and deletes only `bin` and `obj` that sit BESIDE a project file: matching the name alone also hit a package's own executables (9 such directories under `tests\Tests.E2E\node_modules`, so a pruned tree failed Playwright on a missing binary), and a directory a compiler holds open is reported as kept, never as a failure. |
| `Export-TaskPatch.ps1 -Repo -Task -Worktree` | build, coordinator (salvage) | Saves the patch (new, changed and deleted files). Exit 2 lists `OUTSIDE` files that are not in the write set. Exit 3 lists `COMPOSITION-EDIT` lines: a composition file shared ORDERED-BY-MERGE with an unordered open row takes appended lines only (lib `Get-CompositionEditRefusals`; a salvage `-OutFile` export is never refused). |
| `Invoke-Grader.ps1 -Repo -Task -Root [-Label] [-Only grader\|check] [-ExpectRed] [-TimeoutSeconds]` | build, integrate | Runs the row's builder CHECK (`artifacts.check`: clause tests plus impact tests) and its author GRADER (`artifacts.grader`, optional since 2026-10-02) into one log, check first, failing when either fails; the identity line reads `<check>+<grader>`. `-Only` runs one of them (the builder's RED before any edit is `-Only grader`); `NO-GRADER` (exit 4) when neither exists. It runs the scripts with `STREAM_TASK` and `STREAM_SINCE_UTC` set, logs the output and ends the log with `GRADER sha <hash> since <t>`. With `-ExpectRed` it is the RED check. A run against the main tree holds `.streams\main-grader.lock` (one main build at a time); exit 5 = `MAIN-GRADER-BUSY`. A beating run (`-BeatSession`) has a wall-clock limit, `-TimeoutSeconds` (`STREAM_GRADER_TIMEOUT_SECONDS`, else 3600): past it the grader's process tree is ended and the run is `GRADER-TIMEOUT`, exit 8, never RED; `Integrate-Patch.ps1` treats it as an environment failure (`RETRY`). Its child runs `-NonInteractive` with stdin read from an empty file, so a prompt for input cannot wait for ever (G4.T131 sat 2.4 h on a hung `npx` child while its beat kept the claim fresh). Each run redirects the child into files of its own (`<log>.<pid>-<hex>.part/.err/.in`), reads them with FileShare.ReadWrite and never writes them after the child exits, so a process the grader started that outlives it (an MSBuild node, a web host) and still holds them cannot fail the next run of that task (kit item IN-20261015040606-fb72); such leftovers are deleted by a later run once free. |
| `Test-GraderPortability.ps1 -Grader` | plan (import), author | Flags a grader (and the grader a shim calls) that compares file times, reads MyLoop row state, leaves `-Since` unset, pins a commit id or reads git history (`COMMIT-PIN`), names an absolute path under `.loop` (`OUTSIDE-TREE`), delegates to an absolute `.ps1` that is not there (`DEAD-DELEGATE`), or splits a trx `testName` on `(` without trimming it (`UNTRIMMED-TESTNAME`). Exit 0 = `PORTABLE`. |
| `Restore-TaskPatch.ps1 -Repo -Task -Worktree` | build | Lays a bounced task's kept patch on a fresh worktree: `APPLIED` (0), `NO-PRIOR` (1), `CONFLICT` (2, nothing written). |
| `New-SuiteSnapshot.ps1 -Repo -Session -Group -Run [-CopyIgnored <files>] [-Log]` | integrate | Lays down `suite-<group>-<run>`, a detached worktree of the main tree as a builder sees it (HEAD + dirty diff + untracked files, plus the named ignored files such as `.env`), for one step-B run. It holds `main-grader.lock` ONLY while it reads main, never for the run, so author RED re-runs and applies go on while a suite runs. Prints and logs `SNAPSHOT <path> HEAD <sha> ...` so failures are attributed against that sha. The `.streams` input folders are copied file by file (lib `Copy-TreeTolerant`). That copy skips writer temp files (`*.tmp.<pid>.<hex>`) and any file that disappears mid-copy, because authors write those folders while the copy runs (kit item IN-20261010211022-8ba5). Exit 5 = `MAIN-GRADER-BUSY`. The watchdog keeps the newest ready snapshot while its session holds a live integrator lock and reaps every other one. |
| `Invoke-IntegratorRun.ps1 -Repo -Session -Log -Command [-WorkDir]` | integrate | Runs one long step-B command (build, suite) in a child process (in `-WorkDir`, the suite snapshot, when given) with its output in `-Log`, beating `integrator.lock` every 30 s so the watchdog never breaks a live run; exits with the command's code, `LOCK-LOST` (5) when another session holds the lock. The watchdog also skips the orphan reset for an integration row the live lock holder set building. |
| `Enter-Integrator.ps1 -Repo -Session` | integrate | Takes or refreshes the single-integrator lock. Exit 5 = held by another session. |
| `Commit-AdhocChange.ps1 -Repo -Session -Id ADHOC-<yyyyMMdd>-<n> -Worktree -Title -TestProject -TestFilter [-Solution] [-WaitSeconds 1800] [-NoCommit]` | adhoc | Lands one ad-hoc change: exports the worktree's change to `.streams\adhoc\<Id>.patch`, waits for `integrate-patch.lock` then `main-grader.lock`, applies it to main, builds the solution and runs `dotnet test <TestProject> --no-build --filter <TestFilter>`. PASS commits exactly the patch's paths as `<Id>: <Title>` and pushes like Integrate-Patch (git policy rows, fail closed); a red build or test, or a filter that matches no test, reverses it. Outputs `COMMITTED`, `REVERSED` (exit 1), `NOTHING` (2), `REBASE` / `DIRTY` (3), `ADHOC-BUSY` (4). `STREAM_ADHOC_DOTNET` replaces dotnet (self-test). |
| `Integrate-Patch.ps1 -Repo -Session [-Task] [-NoCommit]` | integrate | Applies the next patch in dependency order, then outputs `INTEGRATED` + `COMMITTED`, `BASE-STALE` (before any apply: a dependency patch the builder's base stacked, `base.deps`, changed before it landed, so the verdict was graded against code not on main; task to `ticketed`, patch kept, `lib\Streams.ps1 Get-DependencyBaseDrift`; 2026-10-18 dependency review F1), `REBASE`, `STRAY-EMPTY <id> <files>` (before the apply: 0-byte untracked files at paths the patch creates are moved to `.streams\stray\<id>-<stamp>\` and the check re-run, put back when it still fails; kit item IN-20261019112954-86bc), `ALREADY-APPLIED` (the patch does not apply because main already holds it uncommitted, `git apply --reverse --check` clean: it is graded in place and then committed as an apply; kit item IN-20261019062723-9b6e), `INTEGRATED <id> (already in HEAD)` (HEAD already holds it: the row is integrated with nothing applied or committed), `SUSPECT` (grader defect: task to `planned`, patch kept; only when the patch matches the worktree AND every exact write-set file outside the patch matches between main and the worktree, else the main-tree drift is reported, kit item IN-20261019210040-3dac), `RETRY` (build/IO environment failure on main: task stays `built`, `ticketed` after 3; or any throw after the apply, such as a state write that timed out on the tasks.json lock: the patch is reversed and the task stays `built`), `REVERSED` or `NONE`. Its tasks.json writes wait 90 s for the lock (`STREAM_TASKS_LOCK_WAIT_SECONDS`, 15 s elsewhere). One run per repo: a second concurrent run (even under the same session) prints `DRAIN-BUSY`, exit 4, and does nothing. `NOT-FOCUS <id>` for a built row outside the focus set: it stays built until its group is focus. A patch that fails `--check` only on composition files whose hunks only add lines is merged by those added lines (lib `New-CompositionMergedPatch`, ORDERED-BY-MERGE, kit item IN-20261018134210-ede5): `MERGED <id> <files>`, then `<id>.merged.patch` is applied, graded and committed; anything else is still `REBASE`. |
| `Invoke-Watchdog.ps1 -Repo -Session` | status | Breaks stale claims, the integrator lock and dead inbox holds; reaps worktrees, exporting and attaching a patch first for any task that has not landed and KEEPING a tree whose work cannot become a patch; sweeps stale `tmp*.tmp` and `speedy-*` entries out of the host temp folder (`STREAM_TEMP_ROOT` overrides it, and a self-test must set it to its own scratch), and day-old tool/test leftovers (.NET random-name folders, `Microsoft.NET.Workload_*.log`, `MSBuildTemp*`, `speedy-*`, CrewChief test folders) from the top level of that folder and of `{ScratchRoot}` (`STREAM_SCRATCH_TOP_ROOT` overrides it for self-tests), at most `STREAM_TEMP_SWEEP_MAX` (2000) per pass with a `NOTE LEFT <n>` for the rest. The shapes live in one list, `lib\MachineConfig.psm1` `Clear-AIScratchLeftovers`, which the hourly scheduled task "AI scratch cleanup" (`bin\Clear-AIScratch.ps1`, registered by `install.ps1`, no Claude session) also runs over `{ScratchRoot}` together with its own week-unused-file rule, so an idle machine stays clean too (SMVMTR1's scratch root held 89,249 top-level entries by 2026-10-17). It also sweeps every path `git worktree list` REGISTERS, not just the directories under the roots tasks recorded, so a tree an author or verifier made by hand elsewhere is seen; it sweeps that path itself and never its parent as a root, because a sibling folder there belongs to nobody on this board. Build output (`bin` and `obj` only) is pruned ONLY while the drive is at `warn` or `low` against `Get-DiskNeedMB`, never on every sweep: a `built` tree is waiting for an integrator, and a rebuild costs the next session minutes it pays for nothing while C: has room. A prune keeps the tree and its source, and its `owner\worktrees.md` line names the band and the free space that caused it. Prints one line per action or `QUIET`, then any `JUNK` / `WARN` note. |
| `Get-StreamStatus.ps1 -Repo [-Json]` | status | Read-only 6-line summary (with open inbox counts), or the page model. Dependency flags (2026-10-18): `FOCUS-PULL` (rows of unlisted groups in the focus set because focus work depends on them), `DEP-REVIEW: <n> root(s) ...` (model field `depReview`; owner request IN-20261018143920-ebda, kit item IN-20261018144658-c28b: each unmet dependsOn ROOT that holds 2+ ticketed rows ticketed 2+ days ago behind edges with no reason - no planner text in `dependsWhy`, not a gate / integration / mockup / shared-file edge, and the waiting row's title does not name the dependency; roots are listed by waiter count with their edges, for plan review; `STREAM_DEP_REVIEW_MIN_WAITERS` / `_MIN_DAYS` override the thresholds), `DEP-MOVED` (a building row whose stacked dependency left built). Each group's `phases.tier2` (the page line under its date) reads `pending`, `running`, `ended`, `abandoned`, `closed`, or `held` while `.streams\suites\tier2-hold.json` (`{ since, by, reason, item, groups }`, empty `groups` = every group) records the owner's Tier 2 hold: the planner writes it when it relays such an order and deletes it at the go (kit item IN-20261019194753-16ca). Each role's live sessions split into working (holding a claim) and idle: a claim that comes back `NONE` writes an idle beat to `.streams\idle\<session>.json` and a claim clears it, so an idle poller counts as live inside its role's limit. A live session with no claim that wrote nothing for over 20 minutes counts as `quiet`, not idle: it has stopped claiming. Quiet builders beside claimable rows raise a flag that names them. Beside the build sessions it counts the CLAIMABLE ticketed rows, using `Claim-Task.ps1`'s own gates (released group, no live claim, no live inbox hold, `Test-BuildReady`). The model's `authorRank` lists each planned row that inherits an earlier group, with the row it comes through (`via`). Below the claimable buffer (2 claimable rows per live builder) it raises `PIPELINE DRY: claimable N of target M` with the dominant reason (no author live, RED queue, waiting on unticketed dependency, authors behind, nothing ready), and the page marks the tile. It flags `main tree held <n> min by '<holder>'` when one holder keeps `main-grader.lock` past 20 minutes, and the model's `releases` (shown beside the claimable tile) counts author releases (planned to ticketed) per hour for the last 6 h. When rows are ticketed but none is claimable, a flag names the root rows the waiting chains bottom out on, and what each root needs (`needs author`, `owner gate`, ...). The claimable tile names the focus group; `PIPELINE DRY` gains the reason `focus group <G> exhausted`. The tasks line ends `left to plan N of M clauses (K in no group)`, the model's `leftToPlan`: acceptance clauses (`- id: AC-...` under `acceptance:`) of READY requirement files under `<repo>\docs\requirements` (found from the repo root first) that no row names in its why, title, tests or ticket and no COMMITTED stream-adhoc request names (`.streams\adhoc\<Id>.md` with a `<Id>:` commit on HEAD; kit item IN-20261012012612-8ef6), per group by `scope.include` plus a no-group count. A retired row is its own bucket, `retired`, carved out of `done` like `ticketing` out of `planned`: never blocked, never landed (it feeds no delivery rate, no category total, no uncommitted list), and the clauses it names count as left to plan unless another row names them. It reads `unknown: <reason>` instead of a number when a closed group has a clause no row names (the match is then untrustworthy), the folder is missing, or a READY acceptance list cannot be parsed. |

## Inboxes

Every role has an inbox, `<repo>\.streams\inbox\<skill>.md`. The six are `stream-plan`, `stream-author`,
`stream-build`, `stream-integrate`, `stream-status` and `stream-kit`. Evidence files go in `.streams\inbox\evidence\`.
- Any session or the owner files work or a bug for another role with `Send-InboxItem.ps1`.
- Guidance meant for the future holder of a named row goes into THAT ROW with `Update-Task.ps1 -Note`, never into an inbox. The inbox delivers one way - a role takes an open item - so a request that only a later holder can act on waits in the wrong place: on 2026-09-30 three such items were closed by hand, one 498 minutes old, and one request was filed five times before its sender folded the substance into the row. Reserve an inbox for work a role can take now.
- A request to work ONE NAMED ROW is now deliverable, which it was not before 2026-09-30 21:5xZ: `Claim-Task.ps1 -Task <id>` claims that row when it passes the same gates the sort applies, so "ticket this one next" can be finished rather than only agreed to (kit item IN-20260930211404-3356). Two things still belong in the row instead: guidance for whoever holds it next, and anything that needs no claim.
- Each looping role works the oldest open item at the start of its cycle, within its own write rules, and forwards the
  rest.
- The contract is the header of each file (from `inbox-template.md`): append-only lines, the status is the last line,
  and every line goes through the scripts.
- The lock-checked `taken` is what stops two sessions working one item. Two authors did exactly that on 2026-09-27,
  when lines were appended by hand.
- `stream-status` counts open items per inbox and flags any that sit past their role's limit.

## `/stream-kit inbox`

The kit inbox is worked by one looping session, the kit maintainer: start it with `/loop 10m /stream-kit inbox
repo: <repo>`. Every 10 minutes it lists the open items and works each one; a tick with no open item does nothing
else. Session id (2026-10-05, priority-focus-design 3.5): the `session: <id>` in your start prompt (`<role>-<8 hex>`, chosen by the tab launcher so the cost ledger can find your transcript). Use it on every script call. Without one in the prompt, make one as before. A coordinator works this inbox too; the lock-checked `taken` line stops two sessions working one item.
1. `Get-InboxItems.ps1 -Skill stream-kit -Open`, oldest first. Take each item with `Set-InboxItem.ps1 -Status taken`.
2. Copy the live `scripts\` folder to a stage at `{ScratchRoot}\streams\<repo>\kit-<item>-stage`. Make the change there, on top of the current live files. Never
   copy an older proposal over them.
3. Run both self-tests on the stage. Both `RESULT` lines must read `fails=0`.
4. Re-read each live file and check it still matches the stage's starting copy (another session may have edited it).
   Then publish every changed file with `{ClaudeHome}\bin\Publish-KitFile.ps1 -RelativePath "skills\stream-kit\<path>"
   -Source <stage file> -BaseHash <SHA-256 of the file you staged from, or NEW>` (it writes to `{AIWorkRoot}` and
   hash-checks the write), and run `/machine-config apply`. With `-BaseHash` the publish REFUSES (`DRIFT-REFUSED`, exit
   3, nothing written) when the corpus copy is no longer your base: another session changed it, possibly with a change
   that is published but not yet installed, so the installed copy you staged from is not what you would overwrite. On
   a refusal: stop, `git merge-file` your change onto the current corpus file, re-run both suites, publish with the new
   base. Never copy over drift, even after reporting it (kit item IN-20260930210538-9dc0).
5. A change to a role's contract goes into that role's `SKILL.md` the same way, with its version bumped.
6. Close each item with `done` (what changed, and the test results) or `declined` (why).
7. Report on EVERY tick, an idle one too (owner ruling 2026-10-10). Check the kit inbox (`-Open`) and this session's
   own notifications. Then report: the number of open items; each item this session holds, with its step (staged,
   suites running, publishing); and what the session is working on now, or `idle`. A tick that reports nothing cannot
   be told apart from a dead session.

## Editing `scripts\` outside a kit inbox item

Steps 2 to 4 of `/stream-kit inbox` are the procedure for changing a shared script, and they bind **every** session
that writes anything under `scripts\` or into a role's `SKILL.md` — not only a session working a kit inbox item.
Stage a copy, keep the untouched live files as the base, show any new self-test case RED on the base, get
`RESULT fails=0` from both suites on the stage, re-check the live files against the base for drift, then install once.

There is no lock on that folder. A live edit is invisible to every other session until its next command fails, and
each script is step 1 of a role's cycle, so a script that throws stops all six roles at once.
